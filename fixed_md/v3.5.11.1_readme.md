# IKOS 3.5.11.1 — (v3.5.11 연장) 부동소수점 0 여부의 변환·fabs·비교 전달

## 문제 요약

v3.5.11은 부동소수점 나눗셈의 0 나누기 검사를 추가하고, 값의 0 여부(`FloatZero`)를
분석 상태에 저장했다. 그러나 다음 세 경로에서 0 여부가 사라져, 안전한 나눗셈에도
`floating point divisor might be zero` 오탐이 발생했다.

```c
static void goodG2BSink(float data) {
  int result = (int)(100.0 / data);   // ① float → double 변환(fpext)에서 0 여부 손실
}
static void goodB2G() {
  float data = (float)rand();
  if (fabs(data) > 0.000001) {        // ② fabs 결과를 모름 ③ 비교로 0 아님을 배우지 못함
    int result = (int)(100.0 / data);
  }
}
```

Juliet (Linux, v3.5.10 → v3.5.11) CWE369 float 996 testcase 중 goodG2B 264개,
goodB2G 378개가 TN → FP 로 바뀌었다. (bad 288개는 FN → TP 로 의도대로 개선)

---

## 근본 원인

**파일:** `analyzer/include/ikos/analyzer/analysis/execution_engine/numerical.hpp`

1. `exec_float_conv()`(FPExt/FPTrunc), `exec_int_to_float_conv()`(SIToFP/UIToFP)가
   결과를 무조건 `float_assign_nondet()` 으로 만들었다. Juliet 은 `100.0 / data`
   (double ÷ float)라 항상 `fpext` 를 거친다. 상수 인자는 컴파일러가 미리 접어
   드러나지 않았고, 인자·전역을 거치는 흐름 변형에서만 오탐이 났다.
2. `fabs`/`llvm.fabs.*` 는 모르는 외부 함수라 결과가 TOP 이었다.
3. `exec_float_comparison()` 은 초기화 검사만 하고 아무것도 배우지 않았다
   (`TODO(marthaud): add floating point reasoning`).

## 수정

1. **변환 규칙 (sound)**
   - `fpext`(넓히기): 0 → 0, 0 아님 → 0 아님(좁은 형식의 비정규수도 넓은 형식에선 정규수).
   - `fptrunc`(좁히기): 0 → 0 만 유지. 0 아닌 값은 0/비정규수가 될 수 있어 모름.
   - `sitofp`/`uitofp`: 정수 구간에 0 이 없으면 0 아님, 0 뿐이면 0, 그 외 "0 또는 정규수".
2. **fabs 모델:** `fabs`, `fabsf`, `fabsl`, `llvm.fabs.*` 의 결과는 인자와 같은 0 분류.
   부작용 없음.
3. **비교로 0 아님 학습:** 비교문이 성립하는 경로에서 상수 c 와 비교한
   `x > c (c≥0)`, `x ≥ c (c>0)`, `x < c (c≤0)`, `x ≤ c (c<0)`, `x != 0`, `x == c (c≠0)` 는
   x ≠ 0 을 뜻한다(NaN 은 0 아님으로 분류, unordered 비교도 동일).
   x 가 `fabs(y)`, `fpext(y)`, `fptrunc(y)` 로 정의됐으면 y ≠ 0 도 함께 가정한다(SSA 정의문 역추적).
4. **메모리 재로드:** y 가 메모리에서 읽은 값이고, 읽은 뒤 비교까지 그 블록에서 store 나
   (fabs 외의) 호출이 없고 비교 블록이 그 블록 자체이거나 유일한 후속 블록이면,
   메모리에는 아직 같은 값이 있으므로 좁혀진 값을 그 주소에 다시 기록한다
   (`fscanf(..., &data)` 처럼 주소가 노출된 변수의 재로드 대응).
