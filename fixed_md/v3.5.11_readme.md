# IKOS 3.5.108 — 부동소수점 0 나눗셈 검사와 메모리·함수 간 상태 전달 보완

## 문제 요약

기존 `dbz` 검사기는 정수 나눗셈·나머지만 검사했다. 다음 코드에는 부동소수점
나눗셈이 AR에 남아 있었지만, `-a=dbz`로 분석해도 검사 건수가 0개였고
보고서는 `SAFE`로 출력됐다.

```c
#include <stdio.h>

void test(void) {
  double data = 0.0;
  printf("%g\n", 100.0 / data); // 수정 전: DBZ 검사 없음
}

int main(void) {
  test();
  return 0;
}
```

이번 변경은 기존 `dbz`에 스칼라 부동소수점 나눗셈 검사를 추가한다.
원본은 `--opt=basic`과 `--opt=none` 모두 다음 진단으로 검출된다.

```text
error: floating point division by zero
```

첫 확장에서는 LLVM 상수와 일부 지역 변수만 증명할 수 있어, 필드·배열·전역과
함수 인자에서 불필요한 경고가 발생했다. 최종 구현은 분석 상태에 부동소수점의
0 여부를 저장하고 메모리와 함수 호출을 통해 전달하도록 보완했다.

별도 checker 이름이나 활성화 옵션을 추가하지 않았다. 기존 `-a=dbz`로 사용한다.
이 문서의 `error`는 **제수가 0으로 확정됐다는 검사 결과**이다.
부동소수점 연산의 의미를 정수 0 나눗셈의 undefined behavior와 동일하게
바꾸는 수정은 아니다. LLVM도 두 연산을 구분한다.
관련 명세는 [LLVM 14의 fdiv 설명](https://releases.llvm.org/14.0.0/docs/LangRef.html#fdiv-instruction)을 참고한다.

## 근본 원인

### 원인 1 — DBZ 검사 대상에서 FDiv 제외

**파일:** `analyzer/src/checker/division_by_zero.cpp`

**함수:** `DivisionByZeroChecker::check()`, `check_division()`

기존 검사 대상은 다음 네 정수 연산뿐이었다.

```cpp
UDiv, SDiv, URem, SRem
```

`double`·`float`의 `/`는 AR에서 `FDiv`로 표현되므로 검사 경로에 들어오지 않았다.
원본의 핵심 AR은 다음과 같았다.

```text
// basic
result = 100.0 fdiv 0.0

// none
store &data, 0.0
value = load &data
result = 100.0 fdiv value
```

따라서 원본의 `SAFE`는 제수가 0이 아님을 증명한 결과가 아니라,
해당 연산을 DBZ 검사 대상으로 등록하지 않은 결과였다.

### 원인 2 — 부동소수점 수치 정보가 리터럴과 분석 도메인에서 소멸

**파일:** `analyzer/src/analysis/literal.cpp`

**파일:** `core/include/ikos/core/literal.hpp`

**파일:** `core/include/ikos/core/number/dummy_number.hpp`

**파일:** `core/include/ikos/core/domain/scalar/composite.hpp`

기존 부동소수점 상수는 실제 값 대신 내용이 없는 `DummyNumber{}`로 변환됐다.
`Literal::floating_point()`도 전달받은 인자를 무시하고 새 `DummyNumber{}`를 만들었다.

스칼라 도메인의 `float_assign_nondet()`과 `float_assign()`은 초기화 여부만
설정·복사했다. `0.0`과 `5.0`을 구분할 수 있는 수치 정보는 없었다.

첫 DBZ 확장에서 지역 변수 일부가 정확했던 것은 LLVM 상수 증명 덕분이다.
**지역 변수의 메모리 셀에는 값을 저장하지만 필드의 셀에는 저장하지 못하는
구조였던 것은 아니다.** 공통 부동소수점 값 추적 자체가 빠져 있었다.

따라서 GEP 처리만 고쳐서는 필드·배열·전역과 함수 인자를 함께 해결할 수 없었다.

### 원인 3 — 메모리 읽기·쓰기와 함수 대입에서 0 여부를 전달할 정보 부재

**파일:** `core/include/ikos/core/domain/memory/value.hpp`

**파일:** `analyzer/include/ikos/analyzer/analysis/execution_engine/numerical.hpp`

기존 부동소수점 메모리 쓰기는 값을 임의의 부동소수점으로 처리했다.
읽기는 앞서 수정한 초기화 상태를 복사했지만, 수치 정보는 전달하지 않았다.
함수 인자·반환값의 대입도 초기화 여부만 복사하는 경로를 사용했다.

```c
struct Box { int tag; double divisor; };

static double divide(double x, double y) {
  return x / y; // 5.0으로만 호출해도 첫 확장에서는 warning
}

void examples(void) {
  struct Box box;
  box.divisor = 4.0;
  printf("%g\n", 100.0 / box.divisor); // 첫 확장: warning

  printf("%g\n", divide(100.0, 5.0));  // 첫 확장: warning
}
```

초기화 구문을 대입문으로 바꿔도 문제가 유지된 이유가 여기에 있다.

## 수정 내용

### 수정 1 — 기존 DBZ에 스칼라 부동소수점 나눗셈 등록

**파일:** `analyzer/src/checker/division_by_zero.cpp`

`FDiv`를 검사 대상에 추가하고 정수 구간 검사와 구분하여 처리한다.

| 판별 결과 | DBZ 결과 |
|---|---|
| `+0.0` 또는 `-0.0`으로 확정 | error |
| 0이 아님을 증명 | safe |
| 0일 가능성을 배제할 수 없음 | warning |
| 분석 상태가 bottom이거나 지원하는 증명에서 경로 모순 확인 | unreachable |

확정 미초기화 제수는 기존 `UninitializedVariable` 진단으로 처리한다.
이번 확장은 스칼라 `FDiv`를 대상으로 하며 벡터의 개별 lane 검사는 추가하지 않았다.
정수 DBZ의 기존 구간 판정은 유지한다.

### 수정 2 — 0 여부를 표현하는 FloatZero 추가

**새 파일:** `core/include/ikos/core/value/float_zero.hpp`

**파일:** `core/include/ikos/core/domain/scalar/composite.hpp`

`FloatZero`는 다음 부류와 그 합집합을 표현하는 유한 추상 값이다.

- 0: 양의 0과 음의 0을 포함한다.
- subnormal: 비정규화 수를 별도로 구분한다.
- other: 정상 유한 비영 값, 무한대, NaN을 포함한다.
- top: 분류를 알 수 없는 상태이다.
- bottom: 가능한 상태가 없는 경우이다.

여기서 `other`를 유한수나 양수로 가정해서는 안 된다.
이번 검사는 **제수가 0인지**만 판단하며, NaN이나 다른 부동소수점 예외를
일반적으로 검사하지 않는다.

분류에는 저장된 부동소수점 형식 태그를 함께 기록한다.
다른 형식으로 재해석한 메모리에 이전 분류를 그대로 적용하지 않는다.
모든 바이트가 0으로 확인된 경우에는 별도의 `raw_zero` 태그를 사용한다.

`CompositeDomain`에 변수·메모리 셀별 분류 맵 `_float_zero`를 추가했다.
복사뿐 아니라 포함 관계, 동등성, join, meet, widening, narrowing,
loop·iteration 합류, top·bottom 처리에도 이 맵을 반영했다.
단순히 검사기 안에 가변 전역 캐시를 두는 방식은 사용하지 않는다.

이 정보는 정확한 `5.0` 자체를 저장하는 수치 도메인은 아니다.
`5.0`과 `4.0`은 같은 비영 부류로 표현할 수 있으며 DBZ에는 이 구분으로 충분하다.

### 수정 3 — 리터럴에서 분류를 보존하고 스칼라 대입에 전달

**파일:** `analyzer/src/analysis/literal.cpp`

**파일:** `core/include/ikos/core/number/dummy_number.hpp`

**파일:** `core/include/ikos/core/literal.hpp`

**파일:** `analyzer/include/ikos/analyzer/analysis/execution_engine/numerical.hpp`

- AR 부동소수점 상수를 대상 형식의 LLVM `APFloat`로 해석하여 분류한다.
  호스트 `double` 변환이나 임의의 epsilon 비교는 사용하지 않는다.
- `DummyNumber`가 분류 정보를 담도록 확장하고, 리터럴 생성 시 이를 버리지 않는다.
- 부동소수점 리터럴의 동등성 비교에도 분류 정보를 반영한다.
- 상수 대입은 초기화 상태를 설정한 뒤 분류를 기록한다.
- 변수 대입은 초기화 상태와 분류를 함께 복사한다.

함수 인자·반환값의 기존 대입 경로가 이 연산을 사용하므로, 알려진 분류가
함수 호출을 통해 전달된다. 값을 임의로 추정하거나 특정 함수 이름을 우회하는
별도 처리는 추가하지 않았다.

분류 API는 `float_set_zero()`와 `float_to_zero()`이다.
메모리 도메인, 타입 소거 래퍼, partitioning 도메인에도 전달 경로를 추가했다.
분류를 지원하지 않는 dummy·정수 전용 스칼라 도메인은 보수적으로 top을 반환한다.

### 수정 4 — 필드·배열·전역의 메모리 셀에 분류 저장

**파일:** `core/include/ikos/core/domain/memory/value.hpp`

**파일:** `core/include/ikos/core/domain/scalar/composite.hpp`

`LiteralWriter`는 상수·변수의 부동소수점 분류를 메모리 셀에 저장하고,
`LiteralReader`는 셀의 분류를 읽기 결과에 전달한다.
기존 메모리 주소·오프셋·크기 처리 경로를 이용하므로 필드·원소를 별도로 우회하지 않는다.

```text
store cell, 4.0  → cell의 분류 = 비영
load cell       → 결과의 분류 = 비영
100.0 / 결과    → safe
```

분류는 기존 메모리 동작과 함께 관리한다.

- `dynamic_assign()`은 메모리 복사에 필요한 분류를 보존한다.
- strong update는 이전 분류를 새 분류로 대체한다.
- weak update·분기 합류는 가능한 분류들을 합친다.
- 정수·포인터 저장, 임의 값 저장, forget 등은 이전 부동소수점 분류를 해제한다.
- 초기화된 정수 메모리 셀 전체가 0으로 확인된 부동소수점 읽기는 `raw_zero`로 처리한다.
  기존 메모리 모델이 해당 바이트 범위를 0으로 증명할 수 있는 경우에 한한다.

부동소수점 메모리 읽기의 초기화 상태 복사도 유지한다.
`float_set_zero()`는 초기화 여부를 바꾸지 않으므로, 수치 분류를 추가했다고 해서
미초기화 값을 초기화된 값으로 만들지 않는다.

### 수정 5 — LLVM 증명은 제한된 보조 수단으로 유지

**파일:** `analyzer/src/checker/division_by_zero.cpp`

`FloatDivisorProof`는 대상 형식의 상수 연산과 일부 조건 검사를 보조적으로 증명한다.
단일 대입이며 주소가 노출되지 않은 지역 변수는 저장이 읽기를 지배하는 경우에만
전달한다. volatile 접근, 별칭, 여러 저장, 탈출이 있으면 이 증명을 적용하지 않는다.

지배하는 조건의 참·거짓 경로에서 제수가 0일 수 없는지 확인하여 다음과 같은
단순 사례를 처리한다.

```c
if (data != 0.0) {
  printf("%g\n", 100.0 / data);
}
```

연산 증명에는 깊이와 작업량 제한을 둔다. `strictfp`, 비 IEEE denormal 설정,
unsafe FP 설정, fast-math 플래그와 근사 연산 메타데이터 등에서는 지원하지 않는
상수 연산 증명을 제한한다. 저장된 subnormal도 환경에 따라 0으로 취급될 수 있으면
비영으로 단정하지 않는다.

최종 DBZ 판정은 분석 상태의 분류와 이 증명을 함께 사용한다.
이는 메모리 값 전달을 대신하는 일반적인 LLVM 값 추적기가 아니다.

### 수정 6 — 알 수 없는 외부 함수 호출 후 부동소수점 전역 무효화

**파일:** `analyzer/include/ikos/analyzer/analysis/execution_engine/numerical.hpp`

**함수:** `contains_float()`, `exec_unknown_extern_call()`

기존 외부 함수 정책은 포인터 인수가 가리키는 메모리를 무효화하지만,
인자 없이 변경되는 전역은 일반적으로 유지했다. 새 비영 정보가 다음 코드에서
오래된 상태로 남으면 잘못된 safe 판정이 가능하다.

```c
double divisor = 2.0;
extern void update_global(void);

void example(void) {
  update_global();                 // divisor를 바꿀 수 있음
  printf("%g\n", 100.0 / divisor); // 이전의 2.0을 그대로 신뢰하면 안 됨
}
```

모델이 없는 외부 함수를 호출할 때, 부동소수점 값을 직접 포함한 전역 객체의
메모리를 보수적으로 forget하도록 했다. 배열·구조체도 포함 여부를 확인한다.
이때 **해당 전역 객체 전체**를 무효화하므로 같은 객체의 정수 필드도 영향을 받을 수 있다.

다른 종류의 전역에 대한 기존 정책은 변경하지 않았다.
포인터 전역을 따라 외부 힙까지 모두 탐색하는 기능이나 전체 외부 함수 모델의
건전성을 보장하는 변경은 아니다. 모델이 없는 읽기 전용 함수에서도 이 무효화로
정밀도가 낮아질 수 있다.

### 수정 7 — 보고서가 부동소수점 진단 형식 인식

**파일:** `analyzer/python/ikos/report.py`

부동소수점 DBZ 진단의 정보에는 다음 표시를 저장한다.

```json
{"floating_point": true}
```

보고서는 이를 정수 구간 정보와 구분하여 출력한다.

```text
error: floating point division by zero
warning: floating point divisor might be zero
```

기존 정수 DBZ의 메시지는 유지하고, 부가 정보가 없는 정수 결과도 처리한다.
SARIF의 DBZ 검사 설명에도 부동소수점 나눗셈을 포함했다.

**새 DB를 예전 `ikos-report`로 읽으면 호환성 오류가 발생할 수 있다.**
예전 구현은 모든 DBZ 경고를 정수 구간으로 읽어 다음 예외를 발생시켰다.

```text
interval = Interval.from_dict(report.load_info())
KeyError: 'type'
```

분석기와 같은 `ikos2` 설치 경로의 `ikos-report`를 사용해야 한다.
이 오류만 발생한 경우 올바른 보고서로 기존 DB를 다시 읽으면 되며,
보고서 실행 파일을 맞추기 위해 분석을 다시 수행할 필요는 없다.

| R05 필드에 0.0 대입 | warning / warning | **error / error** |

B13과 G12는 같은 `b13_div()` 안의 같은 나눗셈을 사용한다.
최종 DB에서 호출 문맥별로 error와 safe가 각각 등록되는 것을 확인했다.
공유된 소스 위치에 error가 표시된다는 이유로 G12 호출까지 오류라고 해석하면 안 된다.

| 그룹 | 최종 결과: basic·none 동일 |
|---|---|
| K 기준선 | K01 정수 0 나눗셈 error, K02 safe |
| B 15개 | **모두 검출: error 12개, warning 3개** |
| G 13개 | **경고 없음** |
| R 5개 | R01~R04 경고 없음, R05 error |

G07은 곱셈 사례이므로 DBZ 검사 대상이 아니다. G 그룹의 “경고 없음”이 모든
사례에 DBZ 체크가 존재한다는 뜻은 아니다.

정밀도 확인용 C 그룹은 다음과 같다.

| 사례 | 최종 결과 |
|---|---|
| C01 상수끼리의 0 나눗셈 | 진단 없음: 해당 나눗셈이 컴파일 과정에서 제거됨 |
| C02 `data > 0.0` | safe |
| C03 `data != 0.0` | safe |
| C04 상수 연산으로 만든 0 | error |
| C05 검사한 정수를 부동소수점으로 변환 | warning 유지 |
| C06 `fmod(x, 0.0)` | DBZ 진단 없음: 라이브러리 모델은 추가하지 않음 |
| C07 `fabs(any_d()) + 1.0` | warning 유지 |

## 검증

동일 소스의 임시 Debug 빌드, LLVM 14, 기본 `interval` 도메인으로 확인했다.
임시 빌드는 APRON을 비활성화한 환경이었다. 모든 플랫폼·도메인 조합을 검증한 것은 아니다.

- 사용자 벤치마크를 `basic`·`none`으로 분석하고 호출 문맥별 결과를 확인했다.
- partitioning 도메인의 수동 설정에서도 사용자 벤치마크의 개선 결과를 확인했다.
- 추가 30개 사례를 두 최적화 설정으로 실행한 **60개 구성**이 통과했다.
  반환값, 피호출 함수의 저장, 필드·배열 memcpy, 전부 0인 초기화,
  memset, union 재해석, 부분 바이트 쓰기, 별칭, 여러 대상 포인터,
  분기 합류, fread·외부 호출에 의한 무효화, 초기화·미초기화 사례를 포함했다.
- 기존 임시 DBZ 구성 72개도 분류 전달 보완 후 통과했다.
- 추가 LLVM IR 10개로 PHI, denormal 설정, strict·fast FP 설정,
  근사 메타데이터, 0으로 언더플로하는 연산, 순환 값을 확인했다.
- 일반 텍스트·JSON·SARIF 보고서 **12개 조합**과 Python 구문 검사를 통과했다.
- 분류 값 **576쌍과 그에 대한 삼중 조합**, 스칼라 복사·합류·무효화 및
  초기화 상태 분리 동작을 임시 검증 코드로 점검했다.
- 기존 `core-domain-memory-partitioning`, `analysis-division-by-zero`,
  `analysis-memory` 검사 그룹이 통과했다.
- 빌드, 변경 행의 공백 검사 및 `git diff --check`를 통과했다.

기존 UVA 전체 검사는 `test-33-error.cpp`의 LLVM 가져오기 오류로 중단되어
완료하지 못했다. 동일 비트코드를 수정 전·후 분석기에 각각 입력해 둘 다 종료 코드 5와
다음 오류가 발생하는 것을 확인했다.

```text
error: unexpected llvm constant expression
```

이를 이번 수정의 통과 항목으로 계산하지 않았다.
별도의 초기화·미초기화 추가 사례는 위 60개 구성에 포함하여 확인했다.

프로젝트에 회귀 테스트 파일이나 실행 스크립트를 추가·수정하지 않았다.
추가 검증 코드와 결과는 프로젝트 밖 임시 디렉터리에 두었다.

## 적용 범위와 남은 한계

이번 변경은 스칼라 부동소수점의 **0 여부 전달**을 보완한다.
전체 부동소수점 수치 도메인이나 IEEE 예외 분석기를 구현한 것은 아니다.

- 일반적인 덧셈·곱셈 등의 수치 범위와 변수 사이의 관계는 추적하지 않는다.
  지원하는 LLVM 증명 밖의 연산 결과는 여전히 임의 값으로 처리한다.
- 상수나 기존 분류가 알려진 인자·반환값은 전달하지만, 호출자 조건에서 얻은 모든
  부동소수점 제약을 피호출 함수에 일반적으로 전달한다고 보장하지 않는다.
- 변경되지 않은 지역 변수에 대한 제한된 조건 증명은 지원한다.
  필드·별칭·재로드 전반의 부동소수점 pruning을 구현한 것은 아니다.
- 범위 인덱스, 요약된 메모리, 불명확한 주소와 부분 복사 등에서는 정보가 소실되어
  0이 아닌 실제 값에도 경고가 남을 수 있다.
- 형식이 다른 비트 재해석, PPC double-double, 비표준 FP 환경 등은 보수적으로
  처리한다. 지원하지 않는 형식을 임의의 비영 값으로 가정하지 않는다.
- 스칼라 `FDiv`만 확장했다. 벡터 나눗셈, `FRem`, `fmod` 같은 라이브러리 함수,
  NaN·무한대 전반의 오류 검사까지 추가한 것은 아니다.
- 컴파일러가 나눗셈을 상수 결과로 접어 IR에서 제거하면 현재 검사기는 그 원본 연산을
  검사할 수 없다. 공격적인 최적화·fast-math에서의 원본 소스 검출을 보장하지 않는다.
- 알 수 없는 외부 호출의 부동소수점 전역 무효화는 제한된 보완이다.
  기존 외부 호출·포인터 분석의 모든 가정과 건전성 문제를 해결한 것은 아니다.
- 상태 맵을 추가했으므로 저장·합류·함수 분석 비용이 늘어날 수 있다.
  대규모 프로젝트의 성능 영향은 별도로 측정해야 한다.

C05·C07 등 남은 경고는 위 범위를 넘어서는 정밀도 문제로 분리한다.

## 빌드 및 재확인

소스 반영 후 설치된 `ikos-fixed2`에 적용하려면 재빌드·설치한다.

```bash
/Applications/CLion.app/Contents/bin/ninja/mac/aarch64/ninja \
  -C /Users/baesungmin/Projects/ants/ikos2/cmake-build-debug -j4 install
```

분석 결과 DB를 구분하여 생성한다. 벤치마크의 `argc` 분기를 모두 분석해야 하므로
특정 값의 `--argc` 옵션은 지정하지 않는다.

```bash
ikos-fixed2 -a=dbz --opt=basic -o output-basic.db \
  /Users/baesungmin/Projects/ants/ikos2/bench/test.c

ikos-fixed2 -a=dbz --opt=none -o output-none.db \
  /Users/baesungmin/Projects/ants/ikos2/bench/test.c
```

보고서도 같은 설치본을 사용한다.

```bash
/Users/baesungmin/Projects/ants/ikos2/install/bin/ikos-report output-basic.db
/Users/baesungmin/Projects/ants/ikos2/install/bin/ikos-report output-none.db
```

기존 설치본과 함께 사용할 때는 셸 설정에 별칭을 두면 경로 혼동을 줄일 수 있다.

```bash
alias ikos-report-fixed2="/Users/baesungmin/Projects/ants/ikos2/install/bin/ikos-report"
```

이 별칭은 `ikos-report`의 이름을 프로젝트에서 변경한 것이 아니다.
현재 셸에서 사용할 명령을 특정 설치 경로에 연결하는 설정이다.
