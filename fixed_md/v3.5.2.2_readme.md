# IKOS 3.5.2.2 — 자기 참조 객체에서 null 포인터를 읽으면 분석이 사라지는 문제 수정 (v3.5.2 STL fallback 제거)

## 문제 요약

`std::map`의 `operator[]`, `insert` 등을 호출하면 그 이후 분석이 도달 불가(⊥)가 되어
검사 결과가 사라지는 문제가 있었다. v3.5.2는 STL 호출 결과가 ⊥일 때 외부 함수 호출로
대체하는 fallback으로 이를 우회했지만, 그 대가로 컨테이너를 거친 값이 모두 TOP이 되어
오탐(FP)이 늘었다. 이번 수정은 ⊥가 생기는 근본 원인을 고치고, 더 이상 필요 없어진
v3.5.2의 fallback을 제거한다.

```cpp
#include <cstdio>
#include <map>

void sink(std::map<int, int> dataMap) {
  int data = dataMap[2];
  printf("%d\n", 100 / data);   // 수정 전(fallback 없음): 검사 0개
}                               // v3.5.2(fallback): warning: divisor might be zero
                                // 수정 후: error: division by zero
int main() {
  std::map<int, int> dataMap;
  int data = 0;
  dataMap[0] = data;
  dataMap[1] = data;
  dataMap[2] = data;
  sink(dataMap);
  return 0;
}
```

## 근본 원인

**파일:** `core/include/ikos/core/domain/scalar/composite.hpp`

**함수:** `CompositeDomain::pointer_refine(VariableRef, const PointerSetT&)`

**호출 경로:** `ValueDomain::mem_read()`의 "Handle pointer sets" 단계

값 메모리 도메인은 메모리 위치(객체)마다 그 안에 저장된 **null이 아닌 포인터들**의
대상과 오프셋을 포인터 집합(`PointerSet`)으로 요약해 둔다. 포인터를 읽으면 읽은 값을
이 집합으로 refine 한다.

`PointerSet`은 null 포인터를 표현하지 않는다(`pointer_set.hpp`: "It does not handle null").
그런데 기존 `pointer_refine`은 읽은 포인터가 null일 수 있어도 오프셋을 집합의 오프셋과
교차시켰다.

```cpp
} else {
  this->_points_to_map.refine(p, set.points_to());
  this->_integer.refine(ScalarVariableTrait::offset_var(p), set.offsets());  // null 이어도 수행
}
```

트리 기반 컨테이너는 객체 안에 **자기 자신을 가리키는 필드**와 **null 필드**를 함께 둔다.

| 라이브러리 | 자기 참조 필드 | null 필드 (빈 트리) |
|---|---|---|
| libc++ (`std::__1::__tree`) | `__begin_node_ = &__end_node_` | `__end_node_.__left_` (root) |
| libstdc++ (`std::_Rb_tree`) | `_M_header._M_left/_M_right = &_M_header` | `_M_header._M_parent` (root) |

빈 map에서 root를 읽으면 다음이 일어난다.

```text
객체의 포인터 집합 = { 자기 자신, offset {8} }   // 자기 참조 필드에서 기록됨
읽은 root 값       = null, points_to = {}, offset = 0
offset refine      = {0} ∩ {8} = ∅  →  ⊥
```

이 ⊥가 `__root()`(libc++) → `__find_equal` → `__emplace_unique_key_args`
→ `operator[]` → 호출자로 전파되어, 이후 코드 전체가 도달 불가가 되었다.

Mac(libc++)과 Linux(libstdc++) 모두에서 같은 원인으로 발생한다. 원본 IKOS(`ac7f7c1`)
코드에 있던 문제다.

## 수정

null이 아님이 확실한 포인터에 대해서만 오프셋을 refine 한다. points-to refine은 그대로
유지한다(null 포인터의 points-to는 빈 집합이므로 교차해도 안전).

```cpp
} else {
  this->_points_to_map.refine(p, set.points_to());
  // A pointer set only describes non-null pointers. A null pointer has
  // offset 0, which may be outside of `set.offsets()` (e.g. a node whose
  // other fields point into the same object). Refining the offset of a
  // pointer that may be null would wrongly yield bottom.
  if (this->_nullity.get(p).is_non_null()) {
    this->_integer.refine(ScalarVariableTrait::offset_var(p),
                          set.offsets());
  }
}
```

nullity가 TOP인 포인터도 null(offset 0)일 수 있으므로 refine 하지 않는다. 이렇게 해야
null 가능성을 잘못 제거하지 않는다(sound).

### v3.5.2 STL fallback 제거

**파일:** `analyzer/include/ikos/analyzer/analysis/execution_engine/inliner.hpp`,
`concurrent_inliner.hpp`

v3.5.2에서 추가한 `is_std_function()`과, 사용자 코드에서 호출한 STL 함수의 결과가
normal=⊥일 때 `exec_unknown_extern_call`로 대체하던 코드를 제거한다(v3.5.1 상태로 복원).
`concurrent_inliner.hpp`에 추가됐던 사용되지 않는 `demangle.hpp` include도 제거한다.

v3.5.2의 다른 수정(값이 `undef`인 store를 ⊥ 대신 메모리 forget으로 처리)은 전역 초기화
(`std::piecewise_construct`)에서 생기는 ⊥를 막는 올바른 수정이므로 유지한다.

## 수정 결과

### 최소 예제 (Mac, libc++, `-a dbz`)

| 예제 | 원본 / fallback 없음 | v3.5.2 (fallback) | 수정 후 (fallback 제거) |
|---|---|---|---|
| map `operator[]` 후 sink `100 / data` (Mac, libc++) | 검사 0개 | warning: divisor might be zero | **error: division by zero** |
| 같은 예제 (Linux, libstdc++) | 검사 0개 | warning | warning (⊥ 없이 분석, 아래 한계 참고) |
| map `insert` 후 `100 / z` | 검사 0개 | error | error |
| vector, list, STL 없음 | 정상 | 정상 | 정상 (변화 없음) |

수정 후에는 STL 호출 결과가 ⊥가 되지 않으므로 v3.5.2의 fallback이 필요 없다.

### Juliet

v3.5.2 대비 (Linux 서버, 같은 Juliet 소스·스크립트, 분석기만 다름):

| 항목 | 결과 |
|---|---|
| TP / FN / TN / FP | 6개 CWE 모두 동일 |
| 검사 기록 0개 testcase | 996 → 996 (모두 CWE369 `float_*`, IKOS가 float 미추적) — 새 ⊥ 없음 |
| 변화 범위 | `_74`(std::map) 309개 testcase의 검사 기록 수만 증가 (STL 내부를 실제로 분석) |
| CWE476 `_74` | 첫 `dataMap[0] = data`의 `operator[] might be null` 경고 21건 사라짐 |

fallback을 제거해도 판정 손실이 없고, ⊥ 없이 STL 내부를 sound하게 분석한다.

## 한계 및 후속

- **Linux(libstdc++)에서 map 값 추적 불가:** libstdc++는 트리 삽입·순회 함수
  (`std::_Rb_tree_insert_and_rebalance`, `_Rb_tree_increment`, `_Rb_tree_decrement`)를
  헤더가 아니라 `libstdc++.so`에 둔다. IKOS는 이 함수들을 본문 없는 외부 함수로 처리하므로,
  두 번째 삽입부터 트리 구조와 저장 값을 알 수 없다(`ignored memory write`). 그래서
  Juliet `_74`의 FP/FN은 v3.5.2와 같다. 이 함수들의 구현을 비트코드로 링크하는 방식으로
  별도 개선이 필요하다.
- CWE369 `float_*` 996개는 IKOS가 부동소수점 값을 추적하지 않아 검사 자체가 없다(별개 한계).
