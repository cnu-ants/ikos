# IKOS 3.5.112 — 정확히 1회 실행되는 루프의 상태 합류 오탐 수정

## 수정 범위

**이번 수정은 정확히 1회 실행됨을 증명할 수 있는 제한된 형태의 루프만
대상으로 한다. 2회 이상 반복하거나 반복 횟수가 동적인 루프의 일반적인
상태 합류 문제까지 해결한 것은 아니다.**

카운터가 `0`에서 시작하고, 조건이 `< 1`이며, `1`씩 증가하는지 등을
LLVM 코드에서 검사한다. 이 조건과 제어 흐름의 안전 조건을 모두 만족할 때만
최초 진입과 반복 후 상태가 같은 루프 헤더에서 합쳐지지 않도록 변환한다.

`--opt=basic`과 `--opt=none`에 적용한다. 새 checker나 활성화 옵션은 없다.

---

## 문제 요약

객체를 생성하는 루프와 사용·해제하는 루프가 각각 정확히 한 번 실행되는데도,
포인터가 null일 수 있다는 오탐이 발생했다.

```cpp
#include <stdio.h>

namespace demo {
class Sample {
public:
  int intOne;
  int intTwo;
};

static void test() {
  Sample* data;
  for (int h = 0; h < 1; ++h) {
    data = new Sample;
    data->intOne = data->intTwo = 0;
  }
  for (int j = 0; j < 1; ++j) {
    printf("%d\n", data->intOne); // 수정 전: pointer might be null
    delete data;
  }
}
}

int main() {
  demo::test();
  return 0;
}
```

일반 `new`가 정상 반환하면 결과는 non-null이다. 할당이 실패하여 예외가
발생한 경우에는 해당 정상 실행 경로로 출력까지 진행하지 않는다.
정상 실행에서는 필드가 초기화되고, 해제도 한 번만 수행하므로 위 코드는 안전하다.

현재 소스로 재현했을 때 basic과 none 모두 null 경고가 발생했다.
`uva`, `dfa`도 함께 켜면 포인터·필드의 미초기화 및 double free 경고도 나타났다.

## 근본 원인

### 원인 1 — 카운터와 포인터 상태 사이의 관계가 합류에서 사라짐

**파일:** `core/include/ikos/core/fixpoint/fwd_fixpoint_iterator.hpp`  
**파일:** `core/include/ikos/core/domain/scalar/composite.hpp`

루프 분석은 최초 진입 상태와 반복 후 되돌아오는 상태를 합친다.

```cpp
new_pre_in.join_loop_with(std::move(new_pre_back));
```

이 합류 자체는 정상적인 고정점 분석 절차다. 문제는 정수 카운터, 초기화,
nullity 등의 정보를 별도로 합치면서 이들 사이의 관계를 잃는 데 있다.

| 위치 | 카운터 `h` | 포인터 `data` |
|---|---|---|
| 최초 진입 | 0 | 미초기화, null 여부 불명 |
| 본문 실행 후 | 1 | 초기화됨, non-null |
| 헤더에서 합류 | [0, 1] | 초기화·null 여부 불명 |
| 종료 조건 적용 후 | 1 | 초기화·null 여부 불명이 남음 |

실제로는 `h == 1`이면 본문에서 `data`에 이미 할당했다.
그러나 합류 후에는 이 관계가 남지 않으므로, 종료 조건으로 카운터를 1로
좁혀도 포인터의 초기화·non-null 보장은 복구되지 않는다.

따라서 기존 분류인 “반드시 실행되는 루프에서도 실행 전 상태와 merge”보다
**“루프 카운터와 포인터 상태의 관계를 합류에서 잃어 종료 경로의 상태를
복구하지 못하는 문제”**가 정확하다.

### 원인 2 — 사용·해제 루프에서도 첫 실행과 해제 후 상태가 합쳐짐

두 번째 루프에서도 `j == 0`인 첫 실행 상태와 `delete` 후 `j == 1`인 상태가
합쳐진다. 객체 수명과 카운터의 관계가 사라져, 본문 진입 조건을 적용해도
이미 해제된 상태를 완전히 배제하지 못한다.

해제 처리는 메모리 내용을 잊고 객체 수명을 deallocated로 바꾼다.
이 상태가 다시 루프 헤더에 합류하면서 미초기화·double free 오탐으로 이어진다.

**파일:** `analyzer/include/ikos/analyzer/analysis/execution_engine/numerical.hpp`  
**함수:** `exec_free()` — `delete`도 이 처리 경로를 사용한다.

### new의 null 반환 모델 오류는 아님

같은 파일의 `exec_new()`는 이미 `may_return_null=false`로 할당을 처리한다.
이번 수정에서 `new`의 반환 규칙을 바꾸지는 않았다.
문제는 할당 이후 루프 합류에서 보장이 사라지는 것이다.

## 수정 내용

### 수정 1 — 단일 반복 루프 정규화 패스 추가

**새 파일:** `frontend/llvm/src/pass/simplify_single_iteration_loops.cpp`  
**패스:** `SimplifySingleIterationLoopsPass`

루프를 일반적으로 여러 번 펼치는 기능 대신, 정확히 한 번 실행됨을 증명한
루프의 최초 조건 검사와 마지막 조건 검사를 분리한다.

```text
수정 전:
  진입 → 헤더 → 본문 → 헤더 → 종료
           ↑__________|
           최초·반복 후 상태가 합류

수정 후:
  진입 → 최초 검사 → 본문 → 마지막 검사 → 종료
```

헤더를 복제하여 마지막 검사를 위한 블록을 만들고, 본문 끝을 이 블록으로
연결한다. 증명된 최초 조건은 본문으로, 마지막 조건은 종료로 연결한다.
따라서 두 상태를 같은 헤더에 합칠 필요가 없어진다.

본문은 복제하거나 삭제하지 않는다. 메모리 읽기·쓰기, 할당·해제, 산술 연산,
함수 호출을 보존하여 실제 오류를 검사할 수 있도록 한다.

### 수정 2 — 적용 조건을 제한

주요 조건은 다음과 같다.

- 정수 카운터가 0에서 시작하고, 조건이 signed/unsigned `< 1`이어야 한다.
- 다음 반복 값이 현재 카운터에 1을 더한 값임을 확인해야 한다.
- 진입 블록, 단일 되돌아가기 블록, 헤더의 종료 분기가 확인되어야 한다.
- SSA 카운터는 최초 값과 되돌아오는 값의 PHI 연결을 검사한다.
- 메모리에 남은 카운터는 주소가 노출되지 않은 고정 스택 슬롯이어야 한다.
  초기화·증가 외의 저장, volatile/atomic 접근, 초기화 전 읽기 등을 허용하지 않는다.
- 헤더는 지원하는 PHI·카운터 읽기·비교·분기·디버그 명령으로 제한한다.
- inline assembly, returns-twice 호출, 스택 저장·복원 명령이 있는 함수는 제외한다.

적용할 루프 자체에 하위 루프가 남아 있으면 변환하지 않는다. 다만 안쪽의
단일 반복 루프를 먼저 변환한 뒤 바깥 루프의 조건도 충족하면 순서대로 처리할 수 있다.

큰 함수의 비용을 제한하기 위해 최초 함수 명령 수는 32,768개 이하,
변환은 함수당 최대 128개로 제한한다. 조건을 증명하지 못하면 기존 루프를 유지한다.

### 수정 3 — 종료 후 값과 PHI 연결 보존

루프 종료 후 사용하는 값은 최초 검사 시점의 값이 아니라 마지막 검사 시점의
값이어야 한다. 헤더에서 정의된 값의 외부 사용과 종료 블록의 PHI 입력을
마지막 검사 블록에 맞게 연결한다.

PHI 사이에 서로 참조하는 값이 있을 수 있으므로 외부 사용의 교체 목록을
먼저 수집한 뒤 적용한다. 새로 연결한 사용을 다시 교체하지 않도록 한다.
제어 흐름 변경 후 다음 루프를 처리할 때 지배 트리와 루프 정보를 다시 계산한다.

### 수정 4 — basic과 none 전처리에 등록

**파일:** `frontend/llvm/src/ikos_pp.cpp`  
**파일:** `frontend/llvm/src/pass/initialize.cpp`  
**파일:** `frontend/llvm/include/ikos/frontend/llvm/pass.hpp`  
**파일:** `frontend/llvm/CMakeLists.txt`

패스 선언·초기화·빌드 등록을 추가하고 basic과 none 파이프라인에 연결했다.
`none`에도 분석 정밀도를 위한 이 제한된 정규화가 적용된다.
기존 aggressive 파이프라인은 변경하지 않았다.

## 수정 결과 및 검증

| 원본 예제의 진단 | 수정 전 basic/none | 수정 후 basic/none |
|---|---|---|
| `&data->intOne` might be null | warning | **경고 없음** |
| `data` 또는 `data->intOne` might be uninitialized | warning | **경고 없음** |
| possible double free | warning | **경고 없음** |

첫 번째 루프만 남긴 경우, 두 번째 루프만 남긴 경우, 두 루프를 일반 블록으로
바꾼 경우, 포인터를 처음에 nullptr로 초기화한 경우도 basic/none에서 확인했다.

- 실제 미초기화, 0회 실행, 조건부 초기화, 중복 해제 등 위험 사례
  20개 × basic/none의 **40개 분석 모두 진단을 유지**했다.
- 안전·위험 사례를 합친 임시 C 검증 60개 중 56개가 기대와 일치했다.
  남은 4개는 작은 정수 카운터의 형 변환 및 루프 내 조기 반환 사례를
  basic/none으로 분석한 것으로, 수정 전부터 있던 오탐이 그대로 남았다.
- PHI 교환·자기 참조·종료 PHI·메모리 카운터 등의 LLVM IR 7개를
  basic/none 및 해당 패스만 적용한 설정에서 검증했다.
  **21개 모두 LLVM 검증과 변환 후 실행 결과 확인을 통과**했다.
- 기존 전처리 4개 및 memory·dbz·null·sio·uio·dfa 분석 6개,
  **총 10개 테스트 그룹이 통과**했다.
- 기존 UVA 검사는 실행 가능한 33개 중 32개가 통과했다.
  `test-2-error-2.c`의 기존 기대값 불일치 1건은 남아 있다.
  기존 LLVM importer 오류가 있는 C++ 사례 4개는 제외했다.
- 앞선 범위 인덱스 벤치마크는 basic/none과 도메인·전역 초기화 설정을 조합한
  6가지 구성에서 진단 결과가 유지됐다.

검증 코드는 임시 디렉터리에서 사용했다. 프로젝트에 새 회귀 테스트 파일이나
테스트 실행 스크립트는 추가하지 않았다.

## 남은 한계

**이번 변경을 “반드시 실행되는 모든 루프의 상태 합류 문제 해결”로 분류하면
안 된다. 정확히 1회 실행됨을 지원 조건으로 증명한 루프만 수정했다.**

다음은 이번 패스가 일반적으로 해결하는 범위에 포함되지 않는다.

- 2회 이상 실행되는 루프 및 동적인 반복 횟수
- 다른 시작 값·비교 형태·증가 간격을 사용하는 루프
- 별도의 증명이 필요한 카운터 형 변환이나 주소 노출
- 조기 종료 등 지원 조건을 만족하지 못하는 제어 흐름

그 결과 일부 안전한 루프에서는 기존 오탐이 남을 수 있다.
이번 수정은 도메인의 일반적인 합류 연산을 바꾼 것이 아니라,
증명된 단일 반복 루프에 불필요한 합류가 생기지 않도록 한 전처리 수정이다.

수정 소스를 임시 빌드로 검증했다. 설치된 `ikos-fixed2`에 반영하려면
사용 중인 ikos2 빌드를 다시 설치한다.

```sh
/Applications/CLion.app/Contents/bin/ninja/mac/aarch64/ninja \
  -C /Users/baesungmin/Projects/ants/ikos2/cmake-build-debug -j4 install
```

위 예제를 `single_iteration_new.cpp`로 저장했다면 다음과 같이 확인한다.

```sh
ikos-fixed2 -a=nullity,uva,dfa --opt=basic \
  -o /private/tmp/single-iteration-basic.db single_iteration_new.cpp

ikos-fixed2 -a=nullity,uva,dfa --opt=none \
  -o /private/tmp/single-iteration-none.db single_iteration_new.cpp
```

두 설정 모두 원본 예제의 null·미초기화·double free 경고가 사라지는 것이
확인된 결과다.
