# IKOS 3.5.106 — scanf 계열의 쓰기 범위·반환값 모델 및 비대상 필드 오탐 수정

## 문제 요약

`scanf()`·`fscanf()`·`sscanf()`로 정수를 입력받은 뒤 발생할 수 있는
오버플로를 탐지하는 과정에서, 입력 대상이 아닌 배열 원소와 구조체 필드의
값까지 사라져 오탐이 발생했다. 반환값의 범위를 모르는 데서 오는 오탐도 확인됐다.

```c
// G05: arr[1]만 입력 대상인데 arr[0]의 0까지 잃음
int64_t arr[2] = {0, 0};
fscanf(stdin, "%" SCNd64, &arr[1]);
int64_t r = arr[0] + 1;  // 수정 전: possible signed integer overflow
```

```c
// G06: s.b만 입력 대상인데 s.a의 0까지 잃음
struct Pair { int64_t a, b; } s = {0, 0};
fscanf(stdin, "%" SCNd64, &s.b);
int64_t r = s.a + 1;     // 수정 전: possible signed integer overflow
```

```c
// G10: 대입 억제 변환은 반환값의 대입 개수에 포함되지 않음
int n = fscanf(stdin, "%*d");
int r = n + 1;          // 수정 전: possible signed integer overflow
```

사용자 벤치마크 `bench/test.c`에서 B 그룹 20개는 모두 탐지됐지만,
안전한 G 그룹에서는 G05·G06·G10에 경고가 발생했다.
이번 변경은 이 세 오탐을 해결하며, `--opt=basic`과 `--opt=none` 모두에 적용된다.

### 최초 스칼라 미탐과 이번 변경의 구분

최초에 제시된 다음 미탐은 이미 3.5.101의 공통 함수 호출 처리 수정으로 해결됐다.

```c
int64_t data = 0;
fscanf(stdin, "%" SCNd64, &data);
int64_t result = data + 1;  // 입력이 INT64_MAX이면 signed overflow
```

**관련 커밋:** `bfa65181d263e005ba49f839444127819e6e49e0` (`v3.5.101`)

당시에는 `exec_unknown_call()`이 `ar::InternalVariable`이 아닌 인자를 건너뛰어,
지역변수 주소인 `ar::LocalVariable`을 통한 쓰기 효과가 반영되지 않았다.
포인터 인자를 공통으로 처리하도록 고친 뒤에는 위 `data`의 기존 값 0을 제거하여
가능한 오버플로를 보고한다. 이번 수정은 그 이후 확인된 쓰기 범위와 반환값의
정밀도 문제를 보완한다.

## 근본 원인

### 원인 1 — 형식 문자열을 해석하지 않고 포인터 인자 전체를 변경 가능 대상으로 처리

**파일:** `analyzer/include/ikos/analyzer/analysis/execution_engine/numerical.hpp`

기존 `LibcScanf`·`LibcFscanf`·`LibcSscanf` 처리는 모두
`exec_unknown_call()`에 위임했다. 형식 문자열을 해석하는 전용 모델은 없었다.
따라서 B11의 두 번째 출력 인자, B12의 `%*d` 뒤 인자, B20의 `%s` 뒤 인자에서
경고가 나온 것은 형식과 인자 위치를 정확히 대응시켰기 때문이 아니라,
포인터 인자를 넓게 변경 가능한 것으로 처리했기 때문이다.

이 경로에서 사용한 크기 없는 `mem_forget_reachable(ptr)`는 포인터의 오프셋에
해당하는 필드만 지우지 않고, 같은 기반 메모리 객체의 정보를 제거한다.
그 결과 `&arr[1]`은 `arr[0]`까지, `&s.b`는 `s.a`까지 영향을 주었다.
형식 문자열, `sscanf()`의 입력 문자열, 실제 변환에 쓰이지 않는 추가 포인터
인자도 쓰기 대상으로 취급될 수 있었다.

### 원인 2 — 부분 쓰기 이후 남은 0 초기화 영역을 보존·재사용하지 못함

**파일:** `core/include/ikos/core/domain/memory/value.hpp`

배열이나 구조체의 0 초기화는 메모리 도메인에서 여러 원소를 덮는 하나의 큰
0 셀로 표현될 수 있다. 출력 범위만 지우도록 호출 모델을 바꾸더라도,
그 범위와 겹친 큰 셀을 통째로 삭제하면 나머지 원소의 0 정보가 사라진다.

또한 작은 0 셀 또는 더 큰 0 셀이 남아 있어도, 그 안에서 새 크기의 정수를
읽을 때 해당 읽기 결과를 0으로 구체화하지 못하면 같은 오탐이 남는다.
따라서 호출 모델의 쓰기 크기 제한과 함께 메모리 셀 처리도 보완해야 했다.

### 원인 3 — 반환값을 범위 제한 없는 임의의 int로 처리

**파일:** `analyzer/include/ikos/analyzer/analysis/execution_engine/numerical.hpp`

기존에는 입력 함수의 반환값에 대입 개수의 상한을 반영하지 않았다.
`%*d`는 입력을 소비하지만 대입하지 않으므로 G10의 반환값은 양수가 될 수 없다.
이를 임의의 `int`로 처리하면 `INT_MAX`도 후보에 남아 `n + 1`에서 오탐이 발생한다.

## 수정 내용

### 수정 1 — scanf 계열에 형식 문자열 기반 전용 모델 추가

**파일:** `analyzer/include/ikos/analyzer/analysis/execution_engine/numerical.hpp`

**함수:** `scan_plan()`, `scan_write_size()`, `exec_scanf()`

세 입력 함수의 intrinsic을 `exec_scanf()`에 연결했다. 알려진 형식 문자열을
먼저 끝까지 해석한 뒤, 출력 인자 위치·최대 쓰기 크기·반환값의 대입 개수 상한을
계산한다.

- 정수, 부동소수점, 포인터, 문자·문자열·scanset 변환과 길이 지정자를 처리한다.
- `%*d` 등 대입 억제 변환은 출력 인자와 대입 개수를 소비하지 않는다.
- `%n`은 출력 인자를 소비하지만 반환값의 대입 개수에는 포함하지 않는다.
- `%%`는 출력 인자를 소비하지 않는다.
- 형식 문자열과 `sscanf()`의 원본 문자열은 입력으로 취급한다.
- 형식에서 사용하지 않는 추가 인자는 출력 대상으로 처리하지 않는다.
- `fscanf()`는 스트림 객체를 변경할 수 있다는 기존 효과를 유지한다.

정상적으로 대응되는 출력 인자에는 다음과 같이 크기를 제한한 쓰기 효과를 적용한다.

```cpp
if (write.size) {
  this->_inv.normal().mem_forget_reachable(pointer.var(), *write.size);
} else {
  this->_inv.normal().mem_forget_reachable(pointer.var());
}
```

크기는 분석 대상의 데이터 레이아웃과 인자 포인터의 대상 타입으로 구한다.
특히 `long double`은 LLVM의 값 저장 폭만 사용하면 ABI 패딩을 놓칠 수 있으므로,
`alloc_size_in_bytes()`로 객체의 할당 크기를 사용한다.
예를 들어 x86의 80비트 `long double`이 16바이트 객체이면 16바이트를 변경 가능하게 처리한다.

`%c`는 지정 폭 또는 1개 문자를 대상으로 하며 종결자를 추가하지 않는다.
폭이 있는 `%s`·`%[...]`는 종결자를 포함한 최대 크기를 사용한다.
폭이 없는 문자열 변환, 불투명하거나 호환되지 않는 대상 타입은 해당 출력 객체
전체를 변경 가능하게 처리하여 작은 크기를 임의로 가정하지 않는다.
크기 계산에는 큰 정수를 사용하고, 대상 포인터 크기를 넘으면 정밀 처리를 포기한다.

입력이 실패하거나 일부만 성공하는 경우도 포함하도록 출력 범위를 알 수 없는
상태로 만든다. 모든 출력이 성공했다거나 미초기화 메모리가 초기화됐다고 가정하지 않는다.

### 수정 2 — 변경되지 않은 0 셀 조각 보존 및 읽기 결과 구체화

**파일:** `core/include/ikos/core/domain/memory/value.hpp`

**함수:** `mem_forget_cells()`, `read_realize_single_cell()`

부분 쓰기 범위와 겹친 셀이 **초기화된 정수 0**임이 증명되면,
삭제할 범위 밖의 앞·뒤 조각을 별도의 0 셀로 남긴다.
예를 들어 `[0, 16)`이 모두 0인 상태에서 `[8, 16)`만 입력으로 덮을 수 있다면,
`[0, 8)`의 0 정보는 유지한다.

읽을 범위 전체가 초기화된 하나의 0 셀 안에 포함될 때는 새 읽기 셀의 값도
정수 0으로 설정한다. 이로써 보존된 영역을 다른 크기의 정수로 읽을 때도
0이라는 사실을 사용할 수 있다.

변경될 수 있는 영역의 이전 값은 보존하지 않는다. 일부 바이트만 0이라는
사실로 전체 값을 0으로 만들거나, 미초기화 영역을 초기화된 것으로 바꾸지 않는다.
0의 표현을 이용하므로 엔디언에 따른 임의의 바이트 조합도 필요하지 않다.

### 수정 3 — 반환값에 대입 개수 상한 반영

**파일:** `analyzer/include/ikos/analyzer/analysis/execution_engine/numerical.hpp`

**함수:** `exec_scanf()`

반환값은 초기화된 임의의 정수로 설정한 뒤 다음 제약을 추가한다.

```text
return_value <= 형식에서 가능한 최대 대입 개수
```

`%*d`만 있는 G10은 상한이 0이 되어 `n + 1`이 안전하다고 판정된다.
`EOF`의 구체적인 값을 -1로 고정하지 않으며, 음수 반환 가능성은 남긴다.
반환값과 각 출력 인자의 성공 여부 사이의 관계까지 추적하는 변경은 아니다.

### 수정 4 — 정밀 처리가 불가능한 호출은 기존 모델로 처리

형식 문자열을 알 수 없거나 4096바이트 내에서 종결자를 확인하지 못한 경우,
잘못된 형식, 지원하지 않는 확장·위치 지정 인자, 부족한 출력 인자 등은
기존 `exec_unknown_call()` 처리로 돌아간다.

출력 포인터가 형식 문자열과 같은 기반 객체를 가리킬 수 있거나, 출력 대상의
points-to 집합을 알 수 없는 경우도 같은 경로를 사용한다. 호출 도중 형식이
바뀔 수 있는데 호출 전 형식을 고정해서 해석하는 일을 피하기 위한 처리다.

## 검증

프로젝트에 새 회귀 테스트 파일이나 실행 스크립트를 추가하지 않았다.
별도의 임시 작업 디렉터리에서 소스를 빌드하고 정적 분석 결과를 확인했다.
벤치마크의 오류 연산을 실제로 실행하지는 않았다.

- 사용자 벤치마크: `basic`·`none` 모두 위 판정 확인.
- 추가 C 사례 26개: 두 최적화 설정, 총 52개 조합 통과.
  배열 앞·중간 원소, 0·비0 이웃 필드, 여러 출력 타입, `%n`, 대입 억제,
  bounded 문자열·scanset, 실패 분기, 알 수 없는 형식의 기존 처리 등을 확인했다.
- ABI·엔디언 사례 3개: 두 설정, 총 6개 조합 통과.
  x86 `long double`의 패딩 영역도 변경 가능하게 처리하는지와,
  big-endian 환경에서 비대상 필드의 안전성 및 대상 필드의 경고 유지를 확인했다.
- 기존 메모리 관련 검사 52개 통과, signed overflow 검사 7개 통과,
  double·미초기화 관련 검사 25개 통과.
- 기존 buffer overflow 검사 128개 중 126개 통과.
  기존 불일치인 `test-23-safe.c`·`test-57.c`는 그대로 남았다.
  기존 importer 실행 오류 3개(`test-51.c`, `test-51-unsafe.c`, `test-56.cpp`)는
  이 128개 집계에서 제외했다.

기존 검사 묶음은 메모리 도메인 보완 후 확인했고, 최종 ABI 크기 보완 후에는
사용자 벤치마크와 ABI·엔디언 사례를 다시 확인했다.

## 적용 범위와 남은 한계

이번 변경은 알려진 형식에 대한 **쓰기 범위와 반환값 상한**의 모델을 보완한다.
입력 문자열을 실제로 해석하거나 모든 입력 관련 오탐을 해결하는 변경은 아니다.

- 숫자 변환의 폭만으로 입력값의 수치 범위를 좁히지 않는다.
- 입력 성공·실패와 출력값을 연결하지 않아, 반환값을 검사한 일부 사례에도 경고가 남을 수 있다.
- `sscanf()`에 상수 문자열을 주어도 그 문자열을 숫자로 계산하지 않는다.
- `%n`이 기록하는 문자 개수의 수치 범위를 계산하지 않는다.
- `strtol()`·`atoi()` 등 다른 함수의 정밀도는 이번 수정 범위에 포함하지 않는다.
- 알 수 없는 형식, 비지원 확장, 폭 없는 문자열 출력 등에서는 넓은 쓰기 효과로 인해 오탐이 남을 수 있다.
- 기존 unknown-call 경로의 알 수 없는 포인터 쓰기 처리 정책 자체는 바꾸지 않았다.
- 메모리 보완은 증명된 초기화 정수 0에 한정한다. 임의의 비0 바이트 조합이나
  모든 부분 초기화 상태를 정밀하게 복원하는 일반적인 메모리 모델은 아니다.

따라서 확인한 G05·G06·G10 문제는 해결됐지만, 분석기 전체의 건전성이나
모든 플랫폼·모든 scanf 형식에 대한 완전한 모델을 검증했다고 해석해서는 안 된다.
