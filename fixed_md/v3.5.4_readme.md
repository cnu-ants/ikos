# IKOS 3.5.101 — NULL 검사 후 포인터 사용·메모리 재로드 오탐 수정

## 문제 요약

NULL이 아닐 때만 포인터를 역참조하는 코드에서 `pointer might be null` 경고가
발생하는 문제가 있었다. 검사한 값을 그대로 사용하는 경우뿐 아니라, 배열 원소·
구조체 필드·이중 포인터·전역 변수에서 같은 포인터를 다시 읽는 경우에도 발생했다.

원래 보고된 예시는 다음과 같다.

```cpp
void sink(std::vector<char*> values) {
  char* data = values[2];
  if (data != NULL) {
    printf("%02x\n", data[0]);  // 수정 전: NULL 가능성 warning
  }
}

int main() {
  std::vector<char*> values;
  values.insert(values.end(), 3, (char*)NULL);
  sink(values);
  return 0;
}
```

직접 검사한 포인터의 `data[0]` 접근은 NULL 검사 결과를 유지해야 한다.
또한 다음 코드처럼 검사와 사용 사이에 쓰기가 없다면, 원본 메모리를 다시 읽어도
검사 결과가 반영되어야 한다.

```cpp
struct Holder { char* ptr; };

void use(Holder* h) {
  if (h->ptr != NULL) {
    printf("%02x\n", h->ptr[0]);  // 수정 전: 재로드에서 검사 정보 유실
  }
}
```

이번 수정은 이 두 경로의 NULL 상태 정보 유실을 다룬다.
vector 원소 저장 위치 자체의 주소 추적 문제는 별도 이슈로 남는다.

## 근본 원인

### 원인 1 — 0 오프셋 포인터 연산에서 검사 결과를 다시 불확실하게 만듦

**파일:** `analyzer/include/ikos/analyzer/analysis/execution_engine/numerical.hpp`

**함수:** `exec(ar::PointerShift*)`, `normalize_absolute_zero_nullity()`

`data[0]`은 AR에서 오프셋이 0인 포인터 연산과 메모리 읽기로 표현될 수 있다.
기존 코드는 포인터 연산 후 항상 `normalize_absolute_zero_nullity()`를 호출했다.

이 함수는 points-to 집합에 절대 주소 0이 포함될 가능성이 있고 포인터 오프셋도
0일 수 있으면, NULL 상태를 TOP(NULL 여부 불확실)으로 되돌릴 수 있다.
주소 정보가 불확실한 포인터에서는 분기로 얻은 non-null 제약이 이 과정에서 사라졌다.

`p + 0`은 원래 포인터를 보존하므로, 이 경우의 재정규화는 필요하지 않았다.

### 원인 2 — 메모리 셀과 읽기 결과 사이의 NULL 상태 복사 관계를 보존하지 않음

**파일:** `core/include/ikos/core/domain/nullity/separate_domain.hpp`

**함수:** `SeparateDomain::assign()`, `refine()`

**관련 파일:** `core/include/ikos/core/domain/scalar/composite.hpp`

**관련 함수:** `dynamic_write_pointer()`, `dynamic_read_pointer()`

기존 NULL 상태 도메인은 변수별 상태만 저장했다. 포인터 대입·저장·읽기에서는
현재 NULL 상태를 복사했지만, 복사한 값들이 같은 NULL 상태를 갖는다는 관계는 남기지 않았다.

예를 들어 조건과 본문이 각각 별도의 load를 사용하면 다음과 같이 처리됐다.

```text
v1 = load cell          // cell과 v1 모두 NULL 여부 불확실
assume(v1 != NULL)      // v1만 non-null로 제한
v2 = load cell          // cell은 여전히 불확실하므로 v2도 불확실
load (v2 + 0)           // NULL 가능성 경고
```

`--opt=none`에서는 지역 포인터도 메모리에 저장되고 여러 번 load되는 형태가
많이 남기 때문에, 단순한 `if (p != NULL) p[0]`에서도 이 문제가 나타났다.
`basic`에서는 일부 지역 변수가 정규화되더라도 주소가 노출된 메모리의 재로드에
문제가 남았다. 원인 1의 0 오프셋 처리만 수정해서는 이 경우까지 해결할 수 없었다.

## 수정 내용

### 수정 1 — 오프셋이 확실히 0이면 기존 NULL 제약 유지

**파일:** `analyzer/include/ikos/analyzer/analysis/execution_engine/numerical.hpp`

**함수:** `exec(ar::PointerShift*)`

```cpp
// 수정 전
this->normalize_absolute_zero_nullity(lhs.var());

// 수정 후
if (!this->_inv.normal().int_to_interval(offset_expr).is_zero()) {
  this->normalize_absolute_zero_nullity(lhs.var());
}
```

현재 추상 상태에서 오프셋이 정확히 0임을 증명한 경우에만 재정규화를 생략한다.
0이 아닌 값도 포함하는 오프셋은 기존 정규화 경로를 유지한다.

### 수정 2 — NULL 상태가 같은 복사 관계를 도메인에 보존

**파일:** `core/include/ikos/core/domain/nullity/separate_domain.hpp`

`SeparateDomain`에 `_copies`를 추가하여 NULL 상태가 같은 변수들의 관계를 기록한다.
이 관계는 포인터의 주소나 수치 값 전체의 동일성을 의미하지 않으며,
NULL인지 아닌지가 같다는 사실만 표현한다.

- `assign(x, y)`는 NULL 상태가 불확실할 때 복사 관계를 보존한다.
- `refine()`과 NULL·non-null 단정은 같은 관계에 있는 변수들에 검사 결과를 전파한다.
- 기존 `dynamic_write_pointer()`와 `dynamic_read_pointer()`가 이 대입 연산을
  사용하므로, 원본 메모리 셀·검사에 사용한 읽기 결과·후속 재로드 사이에 결과가 전달된다.
- `set()`과 `forget()`은 변경 대상 변수를 관계에서 분리한다. 다른 복사본 사이의
  유효한 관계는 유지한다.
- 분기 합류(`join`)에서는 양쪽 경로에서 모두 성립하는 관계만 유지한다.
  `meet`, 포함 관계(`leq`), 동등성(`equals`)도 추가된 관계를 반영하도록 수정했다.

예를 들어 `v1 != NULL`을 검사하면 변경되지 않은 `cell`도 non-null로 제한되고,
이후 `v2 = load cell`이 그 상태를 전달받는다. 중간에 셀을 덮어쓰거나 잊으면
이전 검사 결과를 새 값에 적용하지 않는다.

### 수정 3 — 포인터 산술에서는 0 오프셋일 때만 복사 관계 생성

**파일:** `core/include/ikos/core/domain/scalar/composite.hpp`

**함수:** 오프셋을 받는 `pointer_assign()` 오버로드 3개

```cpp
if (this->_integer.to_interval(o).is_zero()) {
  this->_nullity.assign(p, q);
} else {
  this->_nullity.set(p, this->_nullity.get(q));
}
```

위 코드는 변수·선형식 오프셋의 처리이다. 상수 오프셋은 `o.is_zero()`로 판정한다.

0 오프셋일 때만 원본과 결과의 NULL 상태 복사 관계를 유지한다.
그 외에는 기존 NULL 상태 값만 전달하고 관계는 만들지 않는다.
따라서 주소가 바뀐 포인터의 검사 결과가 원본에 잘못 역전파되는 것을 방지한다.

### 수정 4 — 외부 함수에 직접 전달된 지역·전역 변수 주소의 변경 반영

**파일:** `analyzer/include/ikos/analyzer/analysis/execution_engine/numerical.hpp`

**함수:** `exec_unknown_call()`의 포인터 인수 메모리 무효화 처리

기존 코드는 `ar::InternalVariable`인 포인터 인수만 변경 대상으로 처리했다.
따라서 `rewrite(&data)`처럼 지역 변수 주소가 `ar::LocalVariable`로 직접 전달되면
해당 메모리를 무효화하지 않았다. 복사 관계를 보존한 뒤에는 이 누락으로 인해
외부 호출 이후에도 이전 non-null 정보가 남을 수 있었다.

포인터 타입 인수를 `LiteralFactory::get_scalar()`로 해석하도록 변경하여,
지역·전역 변수 주소도 기존 메모리 무효화 경로에 포함시켰다.

```cpp
extern void rewrite(char**);

void use(char* data) {
  if (data != NULL) {
    rewrite(&data);              // data가 NULL로 바뀔 수 있음
    printf("%02x\n", data[0]);  // NULL 가능성 warning 유지
  }
}
```

이 보완은 외부 호출의 기존 정책 전체를 바꾸는 수정은 아니다.
`ignore_unknown_write` 등 기존 옵션·가정은 유지하면서, 직접 전달된 변수 주소가
변경 대상에서 빠지던 경우를 처리한다.

### 검증

수정한 소스로 빌드한 분석기를 사용해 NULL 관련 검사 23개, 메모리 검사 52개,
포인터 오버플로·비교 검사 6개, 앞서 수정한 부동소수점 미초기화 관련 검증 구성
25개가 모두 통과했다. NULL 상태 도메인의 기존 단위 검사 5개도 통과했다.

임시 검증에서는 변수 4개의 NULL 상태로 표현되는 추상 상태 152개에 대해
대입·단정·forget 등을 확인하고, 상태 쌍 23,104개의 합류·교차·포함 관계를 검사했다.
프로젝트에는 이번 재로드 보완을 위한 새 테스트 파일을 추가하거나 기존 테스트를
수정하지 않았다. 검증용 임시 파일은 프로젝트 밖에서 사용했다.

재분석 명령은 다음과 같다. 각 데이터베이스는 별도로 생성한다.

```bash
ikos-fixed2 -a=nullity --opt=basic -o output-basic.db null_check_bench.cpp
ikos-fixed2 -a=nullity --opt=none -o output-none.db null_check_bench.cpp

ikos-report output-basic.db
ikos-report output-none.db
```

## 적용 범위와 남은 문제

이번 벤치마크에서는 직접 NULL 검사와 변경 없는 메모리 재로드 사이에서
검사 정보가 유실되는 오탐이 두 옵션 모두에서 해소됐다.
다음 경고는 별도로 남아 있으며, 이번 수정으로 해결됐다고 판단하지 않는다.

- **V01~V03의 원소 저장 위치 주소:** `values[2]` 또는 반복자 역참조로 원소를
  읽는 단계의 주소에 대한 경고이다. NULL 검사 이후 `data[0]` 경고와 구분한다.
- **V04의 `operator[]` 재호출:** 원소 주소와 다시 읽은 원소 포인터에 대한 경고가 남는다.
- **C01~C03:** 검사 결과를 bool 변수에 저장하거나 검사 함수를 사용하거나,
  여러 조건 사이의 상관관계가 필요한 사례의 경고가 남는다.
- **STL 내부:** allocator의 생성 및 메모리 복사 경로에 대한 경고가 남는다.

따라서 이번 수정은 해당 NULL 검사 정보 보존 문제의 해결이며,
vector 및 STL 관련 NULL 오탐 전체의 해결을 의미하지 않는다.
