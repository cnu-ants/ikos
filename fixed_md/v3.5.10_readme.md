# IKOS 3.5.107 — 작은 signed 타입의 증가·감소 연산에서 unsigned overflow 오탐 수정

## 문제 요약

`signed char`·`short` 등 `int`보다 작은 signed 타입의 `++/--` 연산에서,
실제로는 안전한 연산을 unsigned integer overflow로 보고하는 문제가 있었다.

```c
#include <limits.h>
#include <stdio.h>

static void test(void) {
  signed char data = -1;
  if (data < SCHAR_MAX) {
    ++data;  // 수정 전: error: unsigned integer overflow
    printf("%d\n", data);
  }
}

int main(void) {
  test();
  return 0;
}
```

이 예제의 값은 `-1 → 0`이므로 오버플로가 없다. 조건 검사의 정밀도가 아니라,
작은 signed 타입의 연산을 unsigned 연산으로 분류하는 번역 과정이 문제였다.

첫 수정으로 지역변수와 포인터 경유 등의 사례는 해결됐지만,
사용자가 확장한 `bench/test.c`에서 구조체 필드 G20과 배열 원소 G21에는
같은 unsigned overflow 오류가 남았다.

```c
struct Cnt { signed char c; short s; };

struct Cnt c = {-1, 0};
c.c++;  // G20: 첫 수정 후에도 unsigned overflow error
c.s--;

signed char a[2] = {-1, 0};
++a[0]; // G21: 첫 수정 후에도 unsigned overflow error
--a[1];
```

이번 변경은 최초 수정과 G20·G21 후속 보완을 함께 포함한다.
`--opt=basic`과 `--opt=none` 모두를 대상으로 한다.

## 근본 원인

### 원인 1 — nsw/nuw가 없다는 이유로 unsigned 연산으로 분류

**파일:** `frontend/llvm/src/import/function.cpp`

**함수:** `sign_from_wraps()`, `translate_binary_operator()`

Clang은 원본 예제의 증가 연산을 다음과 같은 LLVM IR로 생성한다.
`basic`에서는 이전 값이 상수로 전파돼 있었다.

```llvm
%next = add i8 -1, 1
```

이 명령에는 `nsw`나 `nuw`가 없다. 기존 `sign_from_wraps()`는 두 플래그가
모두 없으면 unsigned 연산으로 분류했다. 기존 주석도 플래그 없는 연산을
반드시 unsigned로 볼 수 있다고 설명했으나, 작은 signed 타입의 갱신은 반례다.

플래그 없는 LLVM 정수 덧셈은 해당 비트 폭의 모듈러 연산이며,
원래 소스의 signed·unsigned 여부를 플래그 부재만으로 확정할 수 없다.
관련 의미는 [LLVM add 명령 명세](https://llvm.org/docs/LangRef.html#add-instruction)에 설명돼 있다.

결과적으로 AR에서는 다음과 같이 번역됐다.

```text
ui8 result = 255 uadd 1
```

원래 signed 값 -1의 비트 표현이 unsigned 255로 해석된다.
unsigned overflow 검사기는 `255 + 1 > 255`를 정확히 계산하지만,
그 연산을 원본 코드의 unsigned 산술로 취급한 분류가 잘못됐다.
검사 이후 결과를 signed 타입으로 바꾸더라도 이미 등록된 오탐은 없어지지 않는다.

### 원인 2 — 필드·원소 주소의 선언 타입 추적 누락

**파일:** `frontend/llvm/src/import/function.cpp`

**함수:** `translate_narrow_signed_update()` 내부 타입 추적

첫 수정은 디버그 정보와 선언된 포인터 타입으로 signed 여부를 확인했다.
그러나 구조체 필드·배열 원소의 주소는 보통 `getelementptr`로 만들어진다.

```llvm
%field = getelementptr inbounds %struct.Cnt, %struct.Cnt* %object, i32 0, i32 0
%old = load i8, i8* %field
%next = add i8 %old, 1
store i8 %next, i8* %field
```

이 `%field` 자체에는 지역변수의 직접 선언과 같은 강한 타입 근거가 없었다.
첫 수정의 타입 추적은 포인터를 읽는 `load`는 따라갔지만,
`getelementptr`에서 기반 구조체의 필드 타입이나 배열의 원소 타입으로
내려가지 못했다. 따라서 G20·G21은 signed 여부를 확정하지 못하고
기존 unsigned 번역으로 돌아갔다.

## 수정 내용

### 수정 1 — signed 단위 갱신을 넓은 산술과 축소 변환으로 번역

**파일:** `frontend/llvm/src/import/function.cpp`

**함수:** `translate_narrow_signed_update()`, `translate_binary_operator()`

8·16비트 정수의 플래그 없는 `add/sub` 중 피연산자에 `1` 또는 `-1`이 있고,
signed 타입의 근거를 확인할 수 있는 경우를 별도로 번역한다.
`translate_binary_operator()`는 일반적인 signedness 추측에 앞서 이 처리를 시도한다.

원본의 변경 전·후 AR은 다음과 같다.

```text
수정 전:
  ui8 result = 255 uadd 1
  si8 next = bitcast result

수정 후:
  si9 result = -1 sadd 1
  si8 next = strunc result
```

변수인 피연산자는 먼저 원래 비트 폭의 signed 값으로 해석하고,
부호 확장한 뒤 산술 연산을 수행한다. 상수도 signed 의미로 확장한다.
결과는 원래 크기로 축소하고, 기존 결과 변수의 타입이 다르면 비트 변환을 추가한다.

여기서 9·17비트는 C의 `int` 타입을 뜻하지 않는다. 단위 증가·감소의 수학적
결과를 담는 데 한 비트가 더 있으면 충분하므로 사용하는 내부 계산 폭이다.
마지막에 원래 폭으로 축소하여 LLVM 명령의 모듈러 결과를 유지한다.

이 방식은 음수의 비트 표현에서 생기는 carry를 unsigned 소스 오버플로로
보고하지 않는다. 좁은 결과에 임의의 `nsw` 가정을 추가하지도 않으므로,
경계값에서 분석 경로를 bottom으로 만들어 오탐을 숨기지 않는다.

### 수정 2 — signed 여부는 소스 타입의 근거로 판단

**파일:** `frontend/llvm/src/import/function.cpp`

**함수:** `translate_narrow_signed_update()`

`llvm.dbg.value`, 선언된 저장 대상의 타입, 선언된 포인터 변수에서 읽은
포인터 타입을 확인한다. 산술 명령의 사용처만으로 추측한 signedness는
소스가 signed라는 근거로 사용하지 않는다.

계산 결과가 signed 변수와 unsigned 변수 양쪽으로 복사되는 경우에는,
갱신 전 값이 연결되는 디버그 변수 또는 실제 읽고 다시 저장하는 대상을
우선하여 갱신 대상의 타입을 판단한다. 근거가 충돌하거나 signed 여부를
확정할 수 없으면 기존 번역을 유지한다.

### 수정 3 — getelementptr를 따라 필드·원소 타입 추적

**파일:** `frontend/llvm/src/import/function.cpp`

**함수:** `translate_narrow_signed_update()` 내부 `declared_pointer_type`

선언 타입 추적에 `getelementptr` 처리를 추가했다.

- 기반 포인터의 선언 타입을 찾은 뒤 GEP의 인덱스 경로를 따라간다.
- 구조체에서는 해당 필드의 AR 타입을 사용한다.
- 배열 등 순차 타입에서는 원소 타입으로 내려간다.
- 중첩된 구조체·배열과 선언된 포인터를 통한 접근도 같은 방식으로 처리한다.

구조체는 LLVM과 AR의 필드 개수 및 대상 필드의 바이트 오프셋이 맞는지도 확인한다.
레이아웃이 맞지 않거나 타입을 추적할 수 없으면 정밀 처리를 포기한다.
재귀 추적에는 깊이 제한 8을 유지한다.

이 보완으로 G20의 `c.c`·`c.s`와 G21의 `a[0]`·`a[1]`도
지역변수와 같은 signed 단위 갱신 처리에 들어간다.

### 수정 4 — 기존 overflow 검사 대상 유지

**파일:** `frontend/llvm/src/import/function.hpp`

추가한 번역 함수의 선언을 등록했다. 변경된 소스 파일은 이 헤더와
`function.cpp` 두 개이며, overflow 검사기 자체는 변경하지 않았다.

32비트 이상 연산, 벡터 연산, `nsw/nuw`가 있는 연산, signed 타입을
확인하지 못한 연산은 기존 경로를 사용한다. 실제 unsigned 갱신의 기존
진단을 일괄적으로 끄는 방식은 사용하지 않았다.

## 검증

프로젝트에 새 회귀 테스트 파일이나 실행 스크립트는 추가하지 않았다.
임시 디렉터리에서 빌드와 추가 정적 분석을 수행했으며,
오류를 포함한 벤치마크를 실제 프로그램으로 실행하지 않았다.

- 원본 예제: `basic`·`none` 모두 sio/uio 경고 제거 확인.
- 최초 보완 사례 31개: C·C++ 각각 두 설정에서 통과, 총 124개 조합.
  전위·후위 증가·감소, short, 값이 정해지지 않은 입력, 포인터·전역변수,
  signed·unsigned 복사 및 실제 overflow의 진단 유지를 확인했다.
- GEP 추가 사례 22개: C·C++ 각각 두 설정에서 통과, 총 88개 조합.
  구조체·배열·다차원 배열·중첩 객체·packed 구조체·가변 인덱스와
  unsigned 필드·원소의 기존 진단 유지를 확인했다.
- LLVM IR 5개와 C++ 보완 사례 2개: 두 설정에서 총 14개 조합 통과.
  `nsw/nuw` 명령, 타입 정보가 없는 명령의 기존 처리,
  C++ 참조와 `-funsigned-char` 환경을 확인했다.
- 8·16비트의 모든 피연산자 비트 패턴에 대해 `±1`의 덧셈·뺄셈을 확인했다.
  넓힌 signed 결과가 표현 가능하고, 축소 후 비트 패턴이 원래 모듈러 연산과 같았다.
- 기존 unsigned overflow 검사 2개와 signed overflow 검사 7개 통과.
- 사용자 벤치마크는 GEP 보완 후 `basic`·`none` 모두 위 결과 확인.

추가 검사는 확인한 조건에 대한 검증이며, 모든 소스 형태·컴파일 설정의
signedness를 복원할 수 있음을 증명하는 것은 아니다.

## 남은 문제 — G15·G16의 루프 누적합 경고

```c
int sum = 0;
for (signed char i = -10; i < 10; ++i) {
  sum += i;  // 남은 sio warning 위치
}
```

```c
int sum = 0;
for (short i = 10; i > -10; --i) {
  sum += i;  // 남은 sio warning 위치
}
```

이 두 사례에서 작은 타입의 `++/--`는 수정된 경로로 번역된다.
남은 경고는 그 갱신이 아니라 **32비트 signed 누적합**에서 발생한다.
검사 시 확인한 범위는 두 최적화 설정에서 다음과 같았다.

| 사례 | sum 범위 | 더하는 i의 범위 |
|------|----------|----------------|
| G15 | `[-2147483648, 2147483647]` | `[-128, 9]` |
| G16 | `[-2147483648, 2147483647]` | `[-9, 32767]` |

루프 합류·확대 과정에서 누적합의 범위가 int 전체로 넓어지고,
반복 진행과 누적합 사이의 관계가 유지되지 않아 가능한 underflow/overflow를 보고한다.
실제 고정된 반복 횟수를 이용하면 안전하지만, 현재 분석 결과는 이를 증명하지 못한다.

이 문제를 해결하려면 반복 진행·횟수와 누적합을 함께 추적하는 등
별도의 루프 분석 정밀도 개선이 필요하다. 이번 signed 단위 갱신 번역의
완료 범위에는 포함하지 않는다.

## 적용 범위와 한계

- 이번 수정은 signed 근거가 있는 8·16비트 단위 갱신에 한정한다.
  임의의 작은 타입 산술이나 모든 signedness 추론을 바꾸는 변경은 아니다.
- 디버그 타입 정보가 없거나 충돌하는 경우, 복잡한 주소 변환 등으로 선언 타입을
  찾을 수 없는 경우, 추적 깊이를 초과한 경우에는 기존 처리로 돌아가 오탐이 남을 수 있다.
- C01·C02의 좁은 signed 경계값은 원래 폭으로의 변환을 포함한다.
  수정은 분석 대상 LLVM의 비트 결과를 보존하며, 이를 원래 타입의 signed 산술
  overflow로 새로 분류하지 않는다.
- 이 동작은 별도로 논의한 정수 승격 후 축소 변환의 진단 정책을 추가하는 수정과 다르다.
- C04·C05를 포함해 unsigned 타입의 모든 wrap·변환 진단을 재설계하지 않았다.
  특히 C05에 경고가 없다는 기존 결과도 이번 변경으로 달라지지 않았다.
- G15·G16의 루프 누적합 오탐은 남아 있다.
