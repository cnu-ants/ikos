# IKOS 3.5.104 — 미종료 문자열 출력의 범위 초과 미탐 및 후속 오탐 수정

## 문제 요약

`'\0'`이 없는 `char` 배열을 `printf("%s", ...)`로 출력하면 배열 밖까지
읽을 수 있지만, 기존 분석기는 이를 안전하다고 판정했다.

```c
#include <stdio.h>

static void test(void) {
  char data[4] = {'A', 'A', 'A', 'A'};
  printf("%s\n", data);  // 수정 전: safe → 수정 후: buffer overflow error
}

int main(void) {
  test();
  return 0;
}
```

`%s`는 종료 문자를 만날 때까지 읽는다. 위 배열의 네 바이트가 모두 0이 아니므로,
문자열 출력을 계속하려면 배열 범위 밖인 다섯 번째 바이트에 접근해야 한다.
분석에서 필요한 접근 크기는 5바이트이고, 객체의 크기는 4바이트이다.

최초 수정에서는 이 미탐을 탐지했지만, 라이브러리가 써 넣은 종료 문자 정보를
기존 모델이 보존하지 않아 다음 네 안전 사례에서 새 오탐이 발생했다.

| 사례 | 종료 문자를 만드는 방법 | 최초 수정 후 오탐 |
|------|--------------------------|------------------|
| G09 | `snprintf()`의 출력 버퍼 | 크기 16에서 1~17바이트 접근 가능 |
| G10 | `memset(s, 0, sizeof s)` 후 앞의 세 문자만 변경 | 크기 4에서 4~5바이트 접근 가능 |
| G13 | 구조체의 `char[4]` 필드에 `strcpy(..., "AAA")` | 구조체 크기 8에서 1~9바이트 접근 가능 |
| G15 | `calloc(4, 1)` 후 첫 문자만 변경 | 크기 4에서 2~5바이트 접근 가능 |

이번 변경은 최초 미탐 수정과 위 네 오탐의 후속 수정을 함께 포함한다.
종료 문자 유무를 모르면 안전하다고 가정하는 방식으로 검사를 약화하지 않고,
내용을 추적할 수 있는 라이브러리 연산의 실제 쓰기를 모델에 반영했다.

## 근본 원인

### 원인 1 — 문자열 검사가 첫 1바이트의 접근 가능성만 확인

**파일:** `analyzer/src/checker/buffer_overflow.cpp`

**함수:** 기존 `check_string_access()`

기존 구현은 문자열 길이를 추적하지 않는다는 이유로 첫 바이트만 검사했다.
첫 바이트에 접근할 수 있으면 정상 종료된 문자열이라고 가정했다.

```cpp
return this->check_mem_access(stmt, pointer, this->_size_one, if_null, inv);
```

따라서 `data[0]`이 배열 안이라는 사실만으로 안전하다고 판정했고,
종료 문자 없이 `data[4]`까지 읽게 되는 접근을 검사하지 않았다.
같은 가정은 `puts()` 등의 문자열 읽기에도 사용됐다.

### 원인 2 — printf가 포인터 인수의 용도를 구분하지 않음

**파일:** `analyzer/src/checker/buffer_overflow.cpp`

기존 `printf` 계열 검사는 형식 문자열을 해석하지 않고 가변 인수 중 포인터를
문자열 접근으로 검사했다. 이 경로에 종료 문자 검사만 일괄 추가하면,
주소만 출력하는 `%p`나 읽기를 제한하는 `%.4s`에도 잘못된 경고가 생길 수 있다.
`%n`은 결과를 쓰는 포인터이므로 문자열 읽기와 구분해야 한다.

### 원인 3 — 문자열 복사·출력 모델이 대상 내용을 무효화

**파일:** `analyzer/include/ikos/analyzer/analysis/execution_engine/numerical.hpp`

**함수:** `exec_strcpy()`, `exec_strncpy()`, `exec_snprintf()`

기존 모델은 `mem_abstract_reachable()`로 대상 내용을 잊었다.
예를 들어 `strcpy(r.name, "AAA")`가 종료 문자까지 복사해도,
후속 검사에서 `r.name[3] == 0`이라는 사실을 알 수 없었다.
`snprintf()`가 만든 종료 문자와 `strncpy()`의 0 채움도 남지 않았다.

첫 바이트 검사에서는 드러나지 않았던 이 정보 손실이, 종료 문자 검사 추가 후
가능한 범위 초과 경고로 나타났다.

### 원인 4 — memset과 calloc이 바이트 값 0을 충분히 보존하지 않음

**파일:** `core/include/ikos/core/domain/memory/value.hpp`

**함수:** `ValueDomain::mem_set()`

기존 `mem_set()`의 0 채움 처리는 주로 이미 존재하는 메모리 셀을 갱신했다.
문자 단위 셀이 없으면 각 바이트가 0이라는 정보가 새로 만들어지지 않았다.
넓은 셀만 존재하는 경우에는 일부 문자를 다시 쓸 때 그 셀이 제거되어,
쓰지 않은 나머지 바이트의 0 정보도 사라질 수 있었다.

**파일:** `analyzer/include/ikos/analyzer/analysis/execution_engine/numerical.hpp`

**함수:** `exec_calloc()`

기존 보완 코드는 할당 영역이 초기화됐다는 사실을 남겼지만,
8비트 값으로 더 넓은 셀을 쓰는 경로에서는 수치 값이 임의의 값이 됐다.
초기화 여부는 보존해도 문자열 검사에 필요한 바이트 값 0은 알 수 없었다.

## 수정 내용

### 수정 1 — 실제 문자열 읽기의 접근 범위 검사

**파일:** `analyzer/include/ikos/analyzer/checker/buffer_overflow.hpp`

**파일:** `analyzer/src/checker/buffer_overflow.cpp`

`read_string_byte()`, `string_read_size()`, `check_string_read()`를 추가했다.
분석 상태의 복사본에서 바이트를 읽고, 객체 크기·포인터 오프셋·종료 문자·
정밀도 제한을 사용해 검사에 필요한 접근 크기를 계산한다.
검사를 위해 원래 분석 상태의 메모리나 초기화 정보를 변경하지 않는다.

| 확인한 내용 | 판정 방식 |
|-------------|-----------|
| 객체 안에서 확실한 종료 문자를 찾음 | 종료 문자까지의 접근 범위 검사 |
| 객체 끝까지 모든 바이트가 확실히 0이 아님 | 첫 범위 밖 바이트의 접근까지 검사 |
| 바이트가 0일 수도 있고 아닐 수도 있음 | 접근 크기를 구간으로 계산하여 가능한 범위 초과 경고 |
| 내용·크기 등을 충분히 확인할 수 없음 | 첫 바이트 접근 가능성만으로 전체 문자열을 안전하다고 판정하지 않음 |

미초기화 바이트도 확정된 문자 값으로 사용하지 않는다.
원래 예제에서는 접근 크기가 `[5, 5]`로 계산되어 BOA 오류가 발생한다.
이는 실제 문자열 길이가 5라는 뜻이 아니라, 첫 잘못된 읽기를 나타내는 크기이다.

`check_mem_access()`에는 계산한 접근 크기 구간을 전달할 수 있도록 보완했다.
기존 객체 크기·수명·포인터 검사를 사용하며, 보고서에도 접근 크기 구간을 기록한다.

새 검사는 `puts`, `fputs`, `strlen` 및 `printf` 계열의 해당 문자열 읽기에 연결했다.
쓰기 대상 버퍼나 모든 문자열 관련 API에 일괄 적용한 것은 아니다.

### 수정 2 — printf 형식과 정밀도에 따른 인수 검사

**파일:** `analyzer/src/checker/buffer_overflow.cpp`

**함수:** `check_printf_arguments()`

알 수 있는 형식 문자열을 해석하여 가변 인수의 용도를 구분한다.

- `%s`는 좁은 문자열의 종료 문자까지 읽는 접근으로 검사한다.
- `%.Ns`와 `%.*s`는 최대 읽기 바이트 수를 반영한다. 음수 정밀도는 제한이
  생략된 경우로 처리하고, 정밀도 자체가 불확실하면 그 가능성을 보존한다.
- `%p`는 주소 출력이므로 가리키는 메모리의 문자열 읽기를 추가하지 않는다.
- `%n`을 문자열 읽기로 취급하지 않는다. 기존 최소 접근 검사를 유지한다.
- `%%`, 너비·정밀도의 `*`, 위치 지정 인수를 고려하여 실제 인수 위치를 찾는다.
- 형식이 불명확하거나 지원하지 않는 경우, 포인터 인수를 식별할 수 없다는 이유로
  문자열 읽기가 안전하다고 단정하지 않는다.

따라서 종료 문자가 없는 `char[4]`라도 `%.4s`는 범위 안에서 읽고,
`%.8s`는 종료 문자를 찾지 못해 범위를 넘는 것으로 구분한다.

### 수정 3 — memset의 확정된 쓰기를 바이트 셀로 보존

**파일:** `core/include/ikos/core/domain/memory/value.hpp`

**함수:** `ValueDomain::mem_set()`

대상 객체와 오프셋이 하나로 정해지고, 채울 바이트 값도 확정되면,
확실히 쓰이는 구간의 앞부분을 바이트 셀로 만든다.
바이트 값은 `memset`의 의미에 맞게 하위 8비트로 변환한다.
기존 넓은 셀의 0 갱신도 유지하여, 바이트 추적 때문에 기존 정수 정보를
불필요하게 버리지 않도록 했다.

```text
memset(s, 0, 4)  →  s[0]=0, s[1]=0, s[2]=0, s[3]=0 추적
s[0..2] = 'A'    →  s[3]=0 유지
printf("%s", s)  →  4바이트 안에서 종료 확인
```

바이트 셀 생성은 크기의 하한을 사용하며 최대 4096바이트로 제한한다.
길이가 0일 수도 있으면 그 호출이 반드시 0을 썼다고 가정하지 않는다.

함께 확인한 두 구현 문제도 보완했다.

- 변수인 채움 값을 읽는 분기에서 `size.is_machine_int_var()` 대신
  `value.is_machine_int_var()`를 검사하도록 수정했다.
- 크기 하한이 0인 경우 `size_lb - 1`로 확정 쓰기 구간을 만들지 않도록 했다.

### 수정 4 — calloc의 초기화 여부와 0 값 보존

**파일:** `analyzer/include/ikos/analyzer/analysis/execution_engine/numerical.hpp`

**함수:** `exec_calloc()`

기존 초기화 상태 기록 이후, 계산된 보장 초기화 영역에 `mem_set(..., 0, ...)`을
적용한다. 넓은 셀의 0과 제한된 개수의 바이트 셀을 함께 보존한다.
할당 크기가 구간이면 기존과 같이 개수·원소 크기의 하한으로 보장 영역을 계산한다.

메모리 기록 과정에서 임시로 설정한 non-null 상태는 저장해 둔 원래 nullity로
복원한다. `calloc()`이 실패해 NULL을 반환할 가능성을 제거하지 않는다.

이후 `p[0] = 'A'`를 수행해도 `p[1] == 0`이 남으므로 G15는 안전하게 판정된다.

### 수정 5 — strcpy와 strncpy의 실제 복사·0 채움 보존

**파일:** `analyzer/include/ikos/analyzer/analysis/execution_engine/numerical.hpp`

**함수:** `known_string_bytes()`, `write_string_bytes()`, `exec_strcpy()`, `exec_strncpy()`

원본의 바이트 값을 확인할 수 있으면, 대상 전체를 무효화하는 대신 실제 결과를 쓴다.
원본 읽기는 상태의 복사본에서 수행한다.

- `strcpy()`는 원본의 종료 문자까지 확인한 뒤 그 문자도 포함하여 기록한다.
  구조체의 다른 필드처럼 복사 범위 밖의 메모리는 이 정밀 경로에서 유지된다.
- `strncpy()`는 크기가 확정된 지원 범위에서 최대 `n`바이트를 읽는다.
  원본이 먼저 끝나면 나머지를 0으로 채운다.
- 원본이 `n`바이트 안에서 끝나지 않으면 정확히 `n`바이트만 기록하고,
  임의로 종료 문자를 추가하지 않는다.

```c
char safe[4], unsafe[4];
strncpy(safe, "AB", 4);       // 'A', 'B', 0, 0
strncpy(unsafe, "ABCDEFG", 4); // 'A', 'B', 'C', 'D' — 종료 문자 없음
```

이 구분으로 C01의 오탐은 없어지고, B16의 잘린 문자열은 계속 탐지된다.
원본 값이나 크기를 정밀하게 처리할 수 없으면 기존 보수적 모델을 사용한다.

### 수정 6 — 알려진 snprintf 출력과 정확한 종료 위치 기록

**파일:** `analyzer/include/ikos/analyzer/analysis/execution_engine/numerical.hpp`

**함수:** `known_printf_output()`, `exec_snprintf()`

지원하는 형식과 인수 내용을 계산할 수 있고 버퍼 크기가 확정되면,
생성될 문자열을 계산하여 실제 출력 바이트와 종료 문자만 기록한다.
현재 정밀 출력 모델은 리터럴·`%%`·좁은 `%s` 및 그 너비·정밀도 처리를 지원한다.

```text
출력할 전체 길이 = L, 버퍼 크기 = n > 0
실제 문자 수 = min(L, n - 1)
종료 문자 위치 = min(L, n - 1)
반환값 = L
```

버퍼의 마지막 칸을 무조건 0으로 만드는 방식은 사용하지 않는다.
짧은 출력은 실제 종료 위치에만 0을 쓰며, 그 뒤의 바이트를 임의로 초기화하지 않는다.
크기가 0이면 대상 버퍼를 변경하지 않는다.
반환값은 잘리기 전 길이로 기록한다.

G09는 복사한 `AAA` 뒤의 종료 문자를 추적하고,
C02는 잘린 `ABC` 뒤의 종료 문자를 추적하여 안전하게 판정한다.
지원하지 않는 형식이나 불확실한 값·크기는 기존 보수적 처리로 남는다.

## 수정 결과

첨부한 `unterminated_print_bench.c`와 프로젝트의 `bench/test.c` 사례를 기준으로
확인했다. 아래 결과는 문자열 범위 초과 검사에 대한 것으로,
macOS의 `__stdoutp` 주소 정보 부족 경고와 구분한다.

| 그룹·사례 | 최초 문자열 검사 수정 후 | 라이브러리 모델 보강 후 |
|-----------|--------------------------|--------------------------|
| B 18개 | error 13, warning 5 | **error 15, warning 3 — 모두 탐지** |
| G 20개 | G09·G10·G13·G15 오탐 | **문자열 관련 오탐 없음** |
| C01: 짧은 원본을 strncpy로 복사·0 채움 | warning | **safe** |
| C02: snprintf 출력 잘림 | warning | **safe** |
| C03: rand로 채운 내용 불명 문자열 | warning | **warning 유지** |
| C04: 미종료 wchar_t 배열의 `%ls` 출력 | 기존 처리 | **이번 수정 대상 제외** |

B11의 `memset`으로 채운 힙과 B16의 잘린 `strncpy`는 내용을 알 수 있게 되어,
기존 warning에서 error로 강화됐다. B08·B10·B15는 warning으로 남는다.
원래 B01 예제는 `basic`·`none` 모두 4바이트 객체에서 5바이트 접근하는 오류로 나온다.

### 검증 결과

- `--opt=basic`·`--opt=none`과 `interval`·`var-pack-dbm`을 조합한
  네 설정에서 위 B/G/C 결과가 같음을 확인했다.
- 종료 문자를 다시 `'A'`로 덮어쓰면 오류가 발생하는 것을 확인했다.
  `memset`, `calloc`, `strcpy`, `snprintf` 결과 모두를 포함했다.
- 크기 0의 `snprintf`가 버퍼를 변경하지 않는 것, 크기 1의 출력 종료,
  잘리기 전 길이 반환, 너비·정밀도·`%%` 출력, 구조체 이웃 필드 보존을 확인했다.
- `snprintf`가 쓰지 않은 뒷부분의 미초기화 읽기는 오류로 남았다.
  호출을 이유로 버퍼 전체를 초기화한 것으로 처리하지 않는다.
- 길이가 0 또는 4인 `memset` 뒤 미종료 가능성은 warning으로 남았다.
- 8192바이트 `calloc` 버퍼에서 첫 문자만 변경한 문자열 출력도 진단이 없었다.
- 기존 메모리 검사 **52개**, 이전 double 미초기화 관련 구성 **25개**,
  NULL 검사 **14개**가 통과했다.
- 기존 BOA **128개 중 126개 통과**, **2개는 safe 기대값과 warning 판정이 불일치**했다.
  `test-23-safe.c`는 종료 문자 없이 채운 `B[10]`을 `puts`로 출력하고,
  `test-57.c`는 `fgets`의 실패 여부를 확인하지 않고 버퍼를 출력한다.
  이 두 경고는 최초 문자열 검사 수정에서 이미 발생했으며 이번에도 남았다.
  전체 BOA가 통과한 것으로 기록하지 않는다.
- 기존에도 가져오기·실행 오류가 확인된 `test-51.c`, `test-51-unsafe.c`,
  `test-56.cpp`는 위 128개에 포함하지 않았다.
- 빌드와 `git diff --check`를 통과했다.

프로젝트에 새 회귀 테스트 파일을 추가하거나 기존 테스트를 수정하지 않았다.
추가 검증용 코드와 결과는 프로젝트 밖의 임시 디렉터리에서 사용했다.

## 빌드 및 재분석

수정된 소스를 설치된 `ikos-fixed2`에 반영하려면 재빌드·설치한다.

```bash
/Applications/CLion.app/Contents/bin/ninja/mac/aarch64/ninja \
  -C /Users/baesungmin/Projects/ants/ikos2/cmake-build-debug -j4 install
```

`ikos2` 프로젝트에서 다음과 같이 분석한다. 벤치마크는 `argc`의 switch로
사례를 나누므로 전체 사례를 확인할 때 `--argc`를 지정하지 않는다.

```bash
ikos-fixed2 -a=boa -d=interval --opt=basic -o output-basic.db bench/test.c
ikos-fixed2 -a=boa -d=interval --opt=none -o output-none.db bench/test.c

ikos-report output-basic.db
ikos-report output-none.db
```

필요하면 `-d=var-pack-dbm`으로도 같은 결과를 비교한다.
B02·B18·G20의 `__stdoutp` 관련 경고는 이번 문자열 범위 초과 결과와 구분한다.

## 적용 범위와 한계

이번 변경은 좁은 문자열 읽기 검사와, 내용을 확인할 수 있는 라이브러리 쓰기를
보강한 것이다. 다음 범위까지 일반적으로 해결됐다는 의미는 아니다.

- 문자열 스캔, 정밀 복사·출력 및 바이트 셀 생성에는 4096바이트 수준의
  처리 상한이 있다. `calloc` 자체의 할당 크기를 4096바이트로 제한한 것은 아니다.
- 정밀 `strcpy`·`strncpy` 모델은 원본 바이트 값을 확인할 수 있어야 한다.
  `strncpy`의 크기와 정밀 `snprintf`의 버퍼 크기도 확정돼야 한다.
- `snprintf`의 정밀 출력 모델은 모든 printf 형식을 지원하지 않는다.
  숫자·부동소수점·와이드 변환, 위치 지정 출력 등 지원 밖의 형식은 보수적으로 처리한다.
  형식을 읽어 인수의 접근을 검사하는 경로와 실제 출력 바이트를 계산하는 모델은
  지원 범위가 서로 다르다.
- 내용을 잃는 외부 호출, 여러 메모리 대상, 범위 오프셋 또는 불확실한 길이에서는
  종료 문자를 증명하지 못해 경고가 남을 수 있다.
- 경계는 기본적으로 포함 객체의 할당 크기에 의존한다.
  구조체 안의 `char` 배열과 다음 필드 사이의 하위 객체 경계를 일반적으로
  추적하도록 확장한 것은 아니다. B10 탐지만으로 이 문제까지 해결됐다고 보지 않는다.
- 와이드 `%ls`의 전체 종료 문자 검사는 이번 대상이 아니다.
  C04의 무경고를 안전성 증명으로 해석하면 안 된다.
  별도로 완료한 `wcslen()` 모델은 이번 변경에서 수정하지 않았다.
- 문자열 API 전체의 읽기·쓰기 크기를 완전히 모델링한 것은 아니며,
  실제 대규모 프로그램에 대한 성능 영향도 별도로 확인해야 한다.
