# IKOS 3.5.113 — 구조체 값 전달의 포인터↔정수 변환 정보 손실 오탐 수정

## 문제 요약

초기화된 문자열을 가리키는 포인터를 구조체 필드에 저장하고 구조체를 값으로
전달하면, 호출된 함수에서 포인터가 null이거나 읽은 값이 미초기화일 수 있다는
오탐이 발생했다.

```c
#include <stdio.h>

typedef struct {
  char *structFirst;
} Data;

void sink(Data value) {
  char *data = value.structFirst;
  printf("%02x\n", data[0]); // 수정 전: null 및 미초기화 경고
}

static void test(void) {
  char text[] = "Good";
  Data value = {text};
  sink(value);
}

int main(void) {
  test();
  return 0;
}
```

`text`는 초기화되어 있고 `sink()`가 실행되는 동안 유효하다. 구조체를 복사해도
필드의 포인터는 같은 배열을 가리키므로 이 예제는 안전하다.

기존 분류인 “struct + inter + pointer 필드 분석 실패”를 구체화하면,
**구조체 값 전달 시 포인터↔정수 ABI 변환에서 대상 객체·오프셋·nullity 정보가
손실되는 문제**다. 원본에는 해제 연산이 없으므로 원본만으로 double free
분석(`dfa`)의 문제까지 확인한 것은 아니다.

## 근본 원인

### 원인 1 — 구조체 인자가 정수로 전달되는 경로

검증 환경인 macOS arm64 / LLVM 14에서는 포인터 필드 하나를 가진 구조체가
64비트 정수 인자로 변환되어 전달된다. 모든 플랫폼의 ABI가 같은 형태를
사용하는 것은 아니다.

다음은 분석기 내부 코드의 핵심 흐름을 단순화한 것이다.

```text
호출자: 구조체 필드에서 포인터 읽기
        → ptrtosi: 포인터를 64비트 정수로 변환
        → sink(정수 인자)

피호출자: sitoptr: 정수 인자를 포인터로 복원
          → 구조체 필드에 저장
          → 필드를 읽고 역참조
```

따라서 C/C++ 소스에 명시적인 정수 캐스트가 없어도 포인터↔정수 변환을 분석하게
된다. 함수 인자 연결 자체가 구조체의 모든 정보를 버리는 것이 아니라, 이
변환에서 이미 포인터 정보가 사라지는 것이 핵심이다.

### 원인 2 — 포인터를 정수로 바꿀 때 원본 주소 정보를 저장하지 않음

**파일:** `core/include/ikos/core/domain/scalar/composite.hpp`  
**함수:** `scalar_pointer_to_int()`, `scalar_int_to_pointer()`

기존 `scalar_pointer_to_int()`는 null이면 정수 0을 만들고, 절대 주소로 표현된
포인터는 오프셋을 사용했다. 그러나 지역 배열 등 일반 객체를 가리키는 포인터는
구체적인 절대 주소를 알 수 없어 정수 수치 정보를 잊었다.

수치 값을 모르는 것은 타당하지만, 이때 “어느 객체를 가리키던 포인터인가”라는
정보까지 함께 잃었다. 이후 `scalar_int_to_pointer()`는 불명확한 정수만 보고
포인터를 만들므로 다음 정보가 복원되지 않았다.

- `text`라는 실제 대상 객체
- 객체 내 오프셋
- non-null 제약

그 결과 `data`가 null일 수 있다는 경고가 발생하고, `text`의 초기화된 메모리와도
연결되지 않아 `data[0]`의 미초기화 경고가 함께 발생했다. 실제 문자열이
미초기화된 것이 아니라, 초기화된 대상 객체를 더 이상 찾지 못한 것이다.

## 수정 내용

### 수정 1 — 정수로 표현된 포인터의 원본 정보 보존

**파일:** `core/include/ikos/core/domain/scalar/composite.hpp`

포인터를 같은 폭의 정수로 변환할 때 다음 정보를 별도로 저장하도록 수정했다.

| 정보 | 저장 방식 |
|---|---|
| 대상 객체 집합 | 기존 points-to 정보를 정수 변수에도 복사 |
| null 여부 | 기존 nullity 정보를 정수 변수에도 복사 |
| 객체 내 오프셋 | 새 `_int_pointer_offsets`에 구간 스냅샷 저장 |

일반 객체에 임의의 절대 주소를 부여하는 방식은 사용하지 않는다. 정수의 수치
값은 기존처럼 모르는 값일 수 있지만, 해당 값이 변경되지 않은 포인터 표현이라는
사실을 별도로 유지한다.

원본 포인터 변수 자체를 참조하는 방식도 아니다. 변환 당시 정보를 복사하므로
나중에 원본 포인터 변수가 다른 객체를 가리켜도 기존 정수 값의 의미는 유지된다.

이 정보는 다음과 같이 비트 표현을 그대로 유지하는 경로에서 전달된다.

- 같은 폭의 정수 변수 복사와 부호 해석만 바꾸는 `SignCast`
- 정수 인자 및 반환값 전달에 사용되는 기존 복사 연산
- 동적 메모리 셀의 정수 저장·읽기와 셀 복사

정수에서 포인터로 되돌릴 때 보존된 정보가 있으면 대상 객체·오프셋·nullity를
복원한다. 정보가 없으면 기존의 일반 정수→포인터 변환을 그대로 사용한다.

새 상태 요소를 비교, 합류, widening, meet, narrowing, TOP/BOTTOM 처리에도
포함했다. 원본 정보가 없는 경로와 합쳐질 때 한쪽 경로의 정보만으로 복원하지
않도록 한다.

### 수정 2 — 값이 바뀌면 기존 포인터 정보를 무효화

**파일:** `core/include/ikos/core/domain/scalar/composite.hpp`

정수 연산이나 덮어쓰기 이후에도 이전 주소 정보를 유지하면 잘못된 포인터를
안전하다고 판단할 수 있다. 다음 경로에서는 보존한 원본 정보를 제거한다.

- 산술·비트 연산
- 폭이 달라지는 축소·확장 변환
- 상수, 미정 값 또는 임의 값의 대입
- 값을 잊거나 메모리 셀 내용을 변경하는 연산

현재는 `+ 0`처럼 결과적으로 비트가 같을 수 있는 산술 연산도 보수적으로 정보를
제거한다. 임의의 정수 주소 계산까지 정밀하게 추적하는 기능은 아니다.

### 수정 3 — 메모리 도메인의 포인터 요약과 일관성 유지

**파일:** `core/include/ikos/core/domain/scalar/abstract_domain.hpp`  
**파일:** `core/include/ikos/core/domain/memory/value.hpp`

스칼라 도메인에 `scalar_pointer_origin()` 조회 연산을 추가했다. 기본 구현은
정보 없음이며, `CompositeDomain`이 보존한 포인터 정보를 제공한다. 일반 포인터를
저장한 동적 셀도 조회할 수 있도록 했다.

메모리 도메인은 각 객체가 포함할 수 있는 포인터를 `_pointer_sets`로 따로
요약한다. 따라서 스칼라의 변환 정보만 보존하는 것으로는 충분하지 않다.

포인터 표현을 가진 정수 값을 메모리에 저장하면 이 요약에도 원본 포인터를
반영하도록 수정했다. 그렇지 않으면 정수 표현을 구조체 필드로 복사한 뒤
포인터로 읽는 과정에서, 실제 대상 객체가 요약에 없다는 이유로 분석 상태가
bottom이 되어 뒤쪽 검사까지 사라질 수 있다.

반대로 포인터 표현이 저장된 셀을 부분 덮어쓰기하거나 내용을 잊는 경우에는
`forget_cell()` 및 `invalidate_encoded_pointer()`를 통해 해당 객체의 포인터
요약도 보수적으로 잊는다. 이전 대상 객체가 남아 잘못된 안전 판정에 쓰이지
않도록 하기 위한 처리다.

구조체 함수를 우회하거나 모든 포인터 필드를 non-null로 가정하지 않는다.
새 checker나 활성화 옵션도 추가하지 않았다.

## 수정 결과 및 검증

수정한 소스로 임시 빌드하여 `nullity,uva,dfa,boa`를 함께 확인했다.

| 원본 예제 | 수정 전 | 수정 후 |
|---|---|---|
| C / `--opt=basic` | null·미초기화 경고 | 진단 없음 |
| C / `--opt=none` | null·미초기화 경고 | 진단 없음 |
| C++ / `--opt=basic` | null·미초기화 경고 | 진단 없음 |
| C++ / `--opt=none` | null·미초기화 경고 | 진단 없음 |

추가로 스택·전역·힙 객체, 오프셋 포인터, 다중 필드, 중간 함수 호출, 반환값,
정수 저장 및 `memcpy` 경로를 확인했다. 실제 null, 미초기화, 범위 초과,
해제 후 사용 및 이중 해제 사례의 진단도 유지되는지 확인했다.

| 검증 항목 | 결과 |
|---|---|
| 46개 사례 × C/C++ × basic/none | 184개 구성 중 180개 기대 결과와 일치 |
| 진단 없어야 하는 구성 | 88개 중 84개 통과, volatile 관련 4개 오탐 잔존 |
| 진단이 필요한 구성 | 96개 모두 진단 확인 |
| 도메인 연산 직접 검증 | 103개 assertion 통과 |
| 기존 memory·dbz·nullity·sio·uio·dfa 테스트 그룹 | 6개 그룹 모두 통과 |
| 기존 uva 테스트 중 실행 가능한 항목 | 33개 중 32개 통과 |
| 이전 혼합 초기화 범위 벤치마크 | 6개 설정에서 기존 진단과 동일 |
| 이전 1회 루프 관련 예제 | 10개 구성에서 진단 없음 유지 |

진단이 필요한 구성에는 안전한 구조체 전달 뒤에 의도적인 null 역참조를 배치한
사례도 포함했다. 단순히 경고가 줄었는지만 보는 대신, 전달 과정에서 분석 경로가
사라지지 않고 뒤의 실제 오류를 검사하는지도 확인했다.

기존 uva의 `test-2-error-2.c`는 수정 전에도 기대 결과와 불일치했으며 이번에도
남아 있다. LLVM 가져오기 단계에서 실패하는 기존 C++ 사례 4개는 제외했으므로,
uva 전체 테스트가 통과했다고 주장하지 않는다.

검증 코드는 임시 디렉터리에서 사용했으며 프로젝트에 새 회귀 테스트 파일이나
실행 스크립트는 추가하지 않았다.

## 적용 범위와 남은 한계

이번 수정은 **전체 포인터 폭을 유지하면서 비트가 변경되지 않은 정수 표현을
통해 전달되는 포인터 정보**를 보존한다. 원본 구조체 값 전달 예제는 basic과
none 모두 수정되었다.

남은 4개 오탐은 서로 다른 결함 4건이 아니라, `volatile uintptr_t`에 저장한
포인터를 읽는 한 사례를 C/C++ 및 basic/none으로 실행한 결과다. 기존 volatile
읽기 처리가 값을 임의 값으로 바꾸므로 이번 원본 정보 보존만으로 해결되지 않는다.

오프셋은 구간으로 보존하므로 모든 관계형 제약까지 유지하는 것은 아니다.
임의의 비트 조작, 폭 변경 후 재확장, 모든 플랫폼의 구조체 ABI, 모든 구조체의
함수 간 분석을 일반적으로 해결했다고 볼 수는 없다. 외부 미지 함수의 기존
메모리 변경 모델도 이번에 변경하지 않았다.

## 빌드 및 원본 확인 방법

검증은 임시 빌드에서 수행했다. 설치된 `ikos-fixed2`에 적용하려면 수정된
`ikos2`를 다시 빌드·설치해야 한다.

```sh
/Applications/CLion.app/Contents/bin/ninja/mac/aarch64/ninja \
  -C /Users/baesungmin/Projects/ants/ikos2/cmake-build-debug -j4 install
```

위 원본 예제를 `struct_pointer_value.c`로 저장한 후 확인한다.

```sh
ikos-fixed2 -a=nullity,uva,dfa,boa --opt=basic \
  -o /private/tmp/struct-pointer-basic.db struct_pointer_value.c

ikos-fixed2 -a=nullity,uva,dfa,boa --opt=none \
  -o /private/tmp/struct-pointer-none.db struct_pointer_value.c
```

두 설정 모두 원본의 `data[0]`에서 null·미초기화 진단이 나오지 않는 것이
기대 결과다. C++도 같은 코드를 `.cpp` 파일로 저장하여 확인할 수 있다.
