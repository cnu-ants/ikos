# IKOS 3.5.110 — basic 전처리의 부분 초기화 지역 변수 미탐 수정

## 문제 요약

일부 분기에서만 초기화되는 지역 변수를 읽을 때, `--opt=basic`에서
미초기화 가능성을 탐지하지 못하는 문제가 확인됐다.

```c
#include <stdio.h>
#include <stdlib.h>

void test(void) {
  int data;

  if (rand() % 2) {
    /* no initialization */
  } else {
    data = 5;
  }

  if (rand() % 2) {
    printf("%d\n", data); // 기대: warning
  } else {
    data = 5;
    printf("%d\n", data); // 기대: safe
  }
}

int main(void) {
  test();
  return 0;
}
```

두 `rand()` 호출의 결과가 같다는 보장은 없다. 첫 번째 조건이 참이어서
초기화를 건너뛴 뒤, 두 번째 조건도 참이 되면 미초기화된 `data`를 읽는다.
따라서 첫 번째 출력에는 경고가 필요하다. 두 번째 출력은 직전 대입으로 안전하다.

처음에는 `--opt=none`에서 발생하는 미탐으로 분류했지만, **현재 버전에서
직접 재현한 결과는 반대였다. `basic`에서 누락되고 `none`에서는 탐지됐다.**

| 위치 | 올바른 판정 | 수정 전 basic | 수정 후 basic | none (변경 없음) |
|---|---|---|---|---|
| 첫 번째 printf | warning | safe — 미탐 | **warning** | warning |
| 두 번째 printf | safe | safe | safe | safe |

원본 예제의 미탐은 수정했다. 다만 추가 안전 사례에서 발생하는 오탐이 있어,
**미탐과 정밀도 문제를 모두 해결한 범용 수정은 아니다.**

기존 `uva` checker를 사용하며 새 검사기나 활성화 옵션은 추가하지 않았다.

## 근본 원인

### 원인 1 — LLVM mem2reg가 미초기화 경로의 정보를 제거

**파일:** `frontend/llvm/src/ikos_pp.cpp`

수정 전 `basic`은 다음 LLVM 패스로 스택의 지역 변수를 SSA 값으로 변환했다.

```cpp
pass_manager.add(llvm::createPromoteMemoryToRegisterPass());
```

부분 초기화된 변수는 개념적으로 다음과 같이 표현될 수 있다.

```llvm
; 초기화를 건너뛴 경로와 5를 저장한 경로의 합류
%data = phi i32 [ undef, %uninitialized_path ], [ 5, %initialized_path ]
```

LLVM의 최적화 의미에서 `undef`는 특정 값으로 선택될 수 있다. `mem2reg`는
이러한 합류 값을 `5`로 단순화할 수 있고, 이 예제에서는 실제로 첫 번째
printf 인수까지 상수 `5`로 바뀌었다.

```text
수정 전 전처리 후 AR의 첫 번째 출력:
  call @ar.libc.printf(..., 5)
```

컴파일 최적화에는 허용되는 변환이지만, 소스 코드의 미초기화 사용을 찾는
분석에서는 진단에 필요한 정보가 사라진다. LLVM 자체의 구현 오류라기보다,
IKOS가 초기화 분석에 맞게 전처리 변환을 제한하지 않았던 문제다.

### 원인 2 — 초기화 checker가 실행될 때는 복구할 정보가 없음

`uva` checker가 실행되기 전에 메모리 읽기와 미초기화 경로의 값이 사라진다.
따라서 checker에는 초기화된 정수 상수만 전달되어 safe로 판정된다.

원본 코드에 LLVM `mem2reg`만 적용한 IR과, IKOS 전처리 후 AR에서 모두
이 현상을 확인했다. `none`은 해당 SSA 변환을 수행하지 않아 스택의
load/store가 남고, 기존 메모리 초기화 분석으로 경고를 낼 수 있었다.

## 수정 내용

### 수정 1 — 초기화 정보를 보존하는 선택적 SSA 변환 패스 추가

**새 파일:** `frontend/llvm/src/pass/promote_initialized.cpp`

**패스:** `PromoteInitializedPass`

**함수:** `has_store_before_loads()`, `runOnFunction()`

일반 `mem2reg`를 적용하기 전에 각 스택 슬롯의 접근 순서를 확인한다.

1. 기존 LLVM `isAllocaPromotable()` 조건을 만족하는 함수 진입 블록의
   스택 슬롯만 후보로 선택한다.
2. 함수 진입부터 해당 슬롯에 아직 저장하지 않은 경로를 탐색한다.
3. 저장을 만나면 그 경로의 탐색을 종료한다. 저장 전에 읽기를 만나면
   해당 슬롯을 SSA 변환 대상에서 제외한다.
4. 명시적인 `undef` 또는 `poison` 저장이 있는 슬롯도 변환에서 제외한다.
   사용한 LLVM 14에서는 `PoisonValue`가 `UndefValue`를 상속한다.
5. 조건을 통과한 슬롯만 LLVM `PromoteMemToReg()`에 전달한다.
6. 포인터 슬롯의 변환으로 다른 슬롯이 변환 가능해질 수 있으므로,
   더 이상 변환 대상이 없을 때까지 반복한다.

핵심 선택 조건은 다음과 같다.

```cpp
if (slot && llvm::isAllocaPromotable(slot) &&
    has_store_before_loads(slot)) {
  slots.push_back(slot);
}
```

이 검사는 저장 값 자체가 초기화됐음을 새로 가정하지 않는다.
다른 미초기화 값에서 복사된 SSA 값의 초기화 상태는 기존 분석이 처리한다.
저장 없이 읽히는 경로를 `undef` 단순화로 없애지 않도록 하는 것이 목적이다.

CFG의 실제 실행 불가능한 경로까지 보수적으로 포함한다. 읽기 전에 저장된다는
구조적 증명에 실패하면 변수를 메모리에 남기며, 이를 임의로 초기화하거나
경고만 억제하지 않는다. 이 보수성이 추가 오탐의 원인이 될 수 있다.

### 수정 2 — basic에서 새 패스 사용

**파일:** `frontend/llvm/src/ikos_pp.cpp`

```cpp
// 수정 전
pass_manager.add(llvm::createPromoteMemoryToRegisterPass());

// 수정 후
pass_manager.add(ikos_pp::create_promote_initialized_pass());
```

`basic`의 SSA 변환 단계만 교체했다. 초기화가 보장되는 다른 슬롯은 계속
변환하며, 뒤에 실행되는 기존 basic 전처리 단계도 유지했다.

원본의 `data`는 메모리에 남아 분기별 store와 printf 직전 load가 보존된다.
그 결과 기존 메모리 도메인과 UVA checker가 첫 번째 읽기를 초기화 여부
불확실로, 두 번째 읽기를 초기화 상태로 판정한다.

`none`의 파이프라인은 변경하지 않았다. `aggressive`와 사용자가 지정하는
`custom` 파이프라인의 일반 `mem2reg`까지 자동으로 교체하지 않았다.

### 수정 3 — 패스 등록 및 빌드 연결

| 파일 | 변경 내용 |
|---|---|
| `frontend/llvm/include/ikos/frontend/llvm/pass.hpp` | 패스 생성·초기화 함수 선언 |
| `frontend/llvm/src/pass/initialize.cpp` | 패스 등록 |
| `frontend/llvm/CMakeLists.txt` | 새 소스를 ikos-pp 라이브러리에 추가 |

분석기 실행 엔진, 메모리 도메인의 합류 연산, UVA checker 코드는 수정하지 않았다.

## 검증 결과

LLVM 14를 사용하는 임시 Debug 빌드에서 확인했다. 프로젝트에는 새로운
회귀 테스트 파일이나 실행 스크립트를 추가하지 않았다.

### 원본 및 주변 사례

원본은 `basic`과 `none` 모두 첫 번째 printf에서 warning 1건,
두 번째 printf에서는 경고 없음으로 확인했다.

추가 임시 사례는 24개를 각 옵션으로 분석해 총 48회 확인했다.

| 분류 | 사례 수 | 수정 후 basic | none |
|---|---:|---|---|
| 미초기화 위험 사례 | 9 | 모두 탐지 | 모두 탐지 |
| 안전 사례 중 정상 판정 | 13 | 모두 경고 없음 | 모두 경고 없음 |
| 안전 사례 중 남은 오탐 | 2 | warning | warning |

위험 사례에는 완전 미초기화, 부분 초기화, 복사, 반복문 0회 가능성,
초기화 전 첫 반복 읽기, break, 반환값, 포인터 역참조, double 읽기가 포함된다.
첫 반복에서 확정 미초기화 값을 읽는 사례는 error가 타당하며 실제로 error가 나왔다.

정상 판정한 안전 사례에는 상수 초기화, 양쪽 분기 초기화, 중첩 분기 초기화,
읽기 전 덮어쓰기, 미초기화 분기의 조기 반환, do/while, 반복문 내부의
대입 후 읽기, 포인터 복사 등이 포함된다.

### 기존 분석 확인

- 기존 memory, division-by-zero, null-pointer-dereference,
  signed-int-overflow, unsigned-int-overflow, double-free의 6개 분석 테스트
  그룹이 통과했다.
- 실행 가능한 기존 UVA 33개 항목 중 32개가 하네스 기준을 통과했다.
  그중 부분 초기화 사례 2개는 기존 safe 미탐에서 실제 경고로 개선됐다.
- 나머지 UVA `test-2-error-2.c`는 기존 safe에서 warning으로 변경됐다.
  일부 경로에서만 초기화되므로 경고가 필요하지만, 하네스가 허용한
  `error` 또는 기존 `safe`와 달라 테스트 결과는 실패로 기록됐다.
  테스트 기대값은 수정하지 않았다.
- UVA 33~36번 C++ 항목은 이전부터 확인된 LLVM importer 오류 때문에
  이번 실행에서 제외했다. 전체 UVA 테스트가 모두 통과했다는 의미는 아니다.
- assert-prover 그룹은 `test-6.cpp`의 `unexpected llvm constant expression`으로
  중단됐다. 수정 전 전처리기를 사용해도 같은 importer 오류가 발생함을 확인했다.
- 이전 `branch_malloc_bench.c`의 UVA·BOA·DFA 진단은 양쪽 옵션 모두
  기존 결과와 같았다. 이전에 남아 있던 배열 루프·free 한계도 그대로다.

## 남은 한계와 부작용

### 한계 1 — 같은 조건을 다시 검사하는 안전 코드의 오탐

```c
int data;
int condition = rand() % 2;
if (condition)
  data = 5;
if (condition)
  printf("%d\n", data); // 안전하지만 현재 warning
```

동일한 조건을 재사용하므로 출력 시에는 초기화돼 있다. 그러나 CFG를
구조적으로 탐색하면 초기화 분기를 건너뛰고 출력하는 간선 조합까지 포함한다.
새 패스는 이 슬롯을 메모리에 남기고, 현재 메모리 분석은 조건과 초기화 상태의
관계를 합류 후 충분히 복구하지 못해 경고한다.

### 한계 2 — 반드시 한 번 실행되는 반복문 이후 읽기의 오탐

```c
int data;
for (int i = 0; i < 1; ++i)
  data = 5;
printf("%d\n", data); // 안전하지만 현재 warning
```

실제로 반복문은 한 번 실행된다. 하지만 새 패스는 수치 조건을 증명하지 않고
CFG의 0회 경로도 포함하므로 슬롯을 보존한다. 이후 메모리 분석에서도
반복 전 상태와 초기화 상태가 합쳐져 warning이 남는다.

**이 두 사례는 기존 basic에서는 safe였지만 이번 보수적 처리 후 warning으로
바뀌는 새 오탐이다. none에서는 이미 같은 오탐이 있었다.** 이를 단순한 기존
한계로만 표현하거나, 이번 수정으로 모든 안전 사례를 유지했다고 주장하면 안 된다.

두 문제를 해소하려면 실행 가능한 경로에 대한 초기화 증명, 조건과 초기화 상태의
관계 추적, 또는 반복문의 초기화 보장에 대한 추가 분석이 필요하다.
초기화 정보를 다시 제거해 safe로 만드는 방식은 원본 미탐을 되살릴 수 있다.

또한 IKOS에 입력되기 전에 다른 컴파일 최적화가 이미 미초기화 정보를 지운
경우까지 이 패스가 복구하지는 않는다.

## 빌드 및 사용

소스 적용과 임시 빌드 검증을 완료했다. 설치된 `ikos-fixed2`에 반영하려면
프로젝트를 다시 빌드·설치해야 한다.

```sh
/Applications/CLion.app/Contents/bin/ninja/mac/aarch64/ninja \
  -C /Users/baesungmin/Projects/ants/ikos2/cmake-build-debug -j4 install
```

사용자가 저장한 원본 예제를 다음과 같이 각각 분석한다.

```sh
ikos-fixed2 -a=uva --opt=basic -o output-basic.db example.c
ikos-fixed2 -a=uva --opt=none -o output-none.db example.c
```

기대 결과는 두 옵션 모두 첫 번째 printf에 미초기화 가능성 warning 1건이며,
두 번째 printf에는 경고가 없는 것이다.
